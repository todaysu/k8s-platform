## 1. 文档目的

本文档定义轻量化 Kubernetes 多集群运维平台的整体产品范围、核心概念、功能模块、技术架构和首个页面设计，作为后续逐模块设计与开发的统一基线。

本文档回答以下问题：

1. 平台解决什么问题，不解决什么问题。
2. 平台中的集群、节点、命名空间、业务、工作负载和实例分别代表什么。
3. 平台采用怎样的轻量化架构，以及为什么这样选择。
4. 后续约 10 个功能模块如何排序和迭代。
5. 首个功能“多集群健康概览主页”展示什么、如何聚合、如何刷新和如何下钻。

本文档不包含接口字段、数据库表结构、代码目录、具体组件代码和各模块的详细实现方案。这些内容在对应模块进入开发前单独设计。

## 2. 背景与问题陈述

### 2.1 当前环境

- DEV 与 PRD 环境相互隔离。
- 当前约有 30 套测试集群和 30 套生产集群，主要运行在物理机容器环境中。
- 各集群目前以单集群方式管理，缺少统一的多集群视图。
- 集群已有 CPU、内存、硬件和集群类告警，但运维方式以被动接收告警为主。
- Kubernetes Event 已有采集能力，但缺少聚合、归因和趋势分析。
- 业务实例全部无状态，业务流量具备全局路由能力。
- 同一业务会部署在多套集群的同名命名空间内，每套集群运行若干实例。

### 2.2 核心问题

1. 运维人员无法在一个页面快速判断所有集群的整体健康状态。
2. 一个异常业务可能分布在多套集群，当前无法形成跨集群全景视图。
3. 集群、节点、工作负载、实例和 Event 信息分散，问题定位依赖人工逐集群查询。
4. 当前缺少主动巡检、异常聚合和跨资源关联能力。
5. 市面上的多集群平台通常包含发布、应用市场、Helm、多租户和策略治理等大量能力，超出实际需要，部署和维护成本较高。

## 3. 平台定位

### 3.1 一句话定位

面向 Kubernetes 基础设施运维人员，以集群管理为主线、以稳定性为目标的轻量化多集群观察与诊断平台。

### 3.2 核心价值

- **一眼看全局**：在一个主页查看所有集群的健康状态和异常分布。
- **快速下钻**：从全局异常进入集群、节点、工作负载、实例或 Event。
- **跨集群看业务**：以单个业务为中心，比较它在不同集群中的副本、状态、版本和异常。
- **主动发现问题**：从被动告警逐步升级到定时巡检、异常聚合和分析建议。
- **保持轻量**：不承担业务发布和流量治理，不复制 Prometheus 等系统已有能力。

### 3.3 产品边界

平台负责：

- 纳管和维护 Kubernetes 集群连接。
- 汇总集群及其核心资源状态。
- 提供集群、业务和异常三个观察视角。
- 对 Event、资源状态和指标进行关联分析。
- 提供受控的日志查看和容器 Exec 能力。
- 记录关键操作和危险操作审计。

平台不负责：

- 业务发布、灰度发布和版本编排。
- 全局流量调度、Ingress 或 Service Mesh 治理。
- 有状态中间件和数据库专项运维。
- 替代 Prometheus、Alertmanager 或日志平台成为新的数据存储中心。
- 第一版提供通用 Kubernetes YAML 编辑器、Helm 管理或应用市场。
- 第一版提供复杂的多租户和企业级权限体系。

## 4. 目标用户与核心场景

### 4.1 主要用户

#### 平台管理员

- 维护平台配置和管理员账号。
- 纳管、更新和移除集群。
- 维护凭据、环境分类和集群标签。
- 查看操作审计。

第一阶段可由同一个管理员账号承担全部职责。

#### Kubernetes 运维人员

- 查看多集群健康状态。
- 定位节点、工作负载、实例和 Event 异常。
- 查看业务跨集群部署全景。
- 使用日志和受控 Exec 处理问题。

后续如扩展多人使用，再拆分只读人员、运维人员和管理员角色。

### 4.2 核心使用场景

1. 每日进入首页，检查所有 DEV/PRD 集群健康状态。
2. 发现某套集群异常，从卡片下钻到异常节点或实例。
3. 搜索一个业务，查看其在所有集群中的实例分布和异常。
4. 查看近期重复出现的 Warning Event，并识别影响范围。
5. 在告警出现前，通过主动巡检发现节点压力、异常重启或副本不足。
6. 故障处理时查看日志，必要时进入指定容器执行受控命令。
7. 使用 AI 对已有事实进行总结、关联和排查建议生成。

## 5. 产品目标与成功标准

### 5.1 产品目标

1. 将约 60 套集群纳入统一视图，并预留扩展到 100 套集群的能力。
2. 让运维人员在 1 分钟内识别异常集群及主要异常类型。
3. 让运维人员在 3 次页面操作内，从首页进入具体异常资源。
4. 支持按资源名称、命名空间、镜像和 Owner 跨集群定位应用资源。
5. 逐步形成“发现异常—定位范围—查看证据—给出建议—执行操作—留下审计”的闭环。

### 5.2 第一阶段衡量指标

- 已纳管集群的连接状态覆盖率达到 100%。
- 首页能在 3 秒内显示最近一次聚合结果。
- 每个异常状态都能展示原因和数据更新时间。
- 单套集群不可达时，其他集群仍能正常展示和刷新。
- 首页所有异常均能下钻到对应集群或资源视图。
- 不在页面、日志或数据库中暴露明文 Kubernetes Token、客户端私钥或其他连接凭据。

## 6. 核心概念模型

### 6.1 概念关系

```text
平台
 └── 集群 Cluster
      ├── 节点 Node
      └── 命名空间 Namespace
           └── 业务 Business
                └── 工作负载 Workload
                     └── 实例 Instance（Pod）

同一个 Business
 ├── 集群 A / 同名 Namespace / Workload / n 个实例
 ├── 集群 B / 同名 Namespace / Workload / n 个实例
 └── 集群 C / 同名 Namespace / Workload / n 个实例
```

### 6.2 集群 Cluster

平台纳管的一个独立 Kubernetes 集群，是运维视图、连接凭据和健康状态的顶层边界。

主要属性包括：

- 集群唯一标识和显示名称。
- 环境类型：DEV、PRD，未来可扩展其他类型。
- 公司技术栈标签：`TCS`、`CMBK8S` 或 `OCP`；纳管时人工选择，避免自动识别错误。
- API Server 和 Kubernetes 版本。
- 连接状态和最近检查时间。
- 集群标签，如机房、区域、用途或负责人。
- 凭据状态和凭据更新时间。

第一版通过集群名称和 Kubeconfig 纳管，默认选择 Kubeconfig 的 `current-context`。平台不长期保存原始 Kubeconfig，只保存建立连接所必需的加密字段。

### 6.3 节点 Node

集群的计算资源载体，对应 Kubernetes Node。

重点关注：

- Ready 状态。
- 调度状态。
- MemoryPressure、DiskPressure、PIDPressure、NetworkUnavailable。
- Kubernetes 版本、运行时和节点角色。
- CPU、内存、Pod 容量与使用情况。
- 节点上的异常实例数量。

### 6.4 命名空间 Namespace

集群内的逻辑隔离范围，用于组织业务及其 Kubernetes 资源。

命名空间不是业务本身，因为一个命名空间可能包含多个业务。平台将命名空间作为业务识别和筛选的重要维度，但不会默认将“一个命名空间”等同于“一个业务”。

### 6.5 业务 Business

跨集群存在的逻辑业务，是“单业务跨集群全景视图”的主体。

推荐采用以下识别规则：

1. **目标规则**：通过统一 Kubernetes Label，例如 `ops.platform/business-id`，为跨集群同一业务提供稳定身份。
2. **第一版兼容规则**：在尚未统一 Label 时，以“命名空间 + 工作负载名称”形成临时业务键。
3. 如果同一业务由多个工作负载构成，后续通过业务映射配置将多个工作负载归入同一个 `business_id`。

业务至少包含：

- 业务唯一标识和显示名称。
- 所属命名空间。
- 跨集群部署范围。
- 关联工作负载集合。
- 期望实例数、实际实例数和异常实例数。
- 镜像版本分布和最近变更时间。

### 6.6 工作负载 Workload

负责维护实例副本的 Kubernetes 控制器资源。

第一阶段以无状态业务为主，优先支持 Deployment；同时识别 DaemonSet 和 StatefulSet，但不提供有状态业务专项运维能力。

重点关注：

- 期望副本、可用副本和不可用副本。
- 更新状态和镜像版本。
- 关联实例及其状态。
- 调度失败、拉取镜像失败、探针失败等异常。

### 6.7 实例 Instance

业务实际运行单元，第一版对应 Kubernetes Pod。

重点关注：

- Phase、Ready 状态和所在节点。
- 容器数量、容器状态和重启次数。
- 创建时间、运行时长和镜像版本。
- Pending、CrashLoopBackOff、ImagePullBackOff、OOMKilled 等异常。
- 关联 Event、日志和 Exec 入口。

### 6.8 核心模型约束

- Kubernetes API 是资源当前状态的事实来源。
- 平台数据库保存平台配置、关联关系、健康快照和审计信息，不复制保存所有 Kubernetes 资源。
- 指标系统是 CPU、内存和趋势数据的事实来源。
- 业务身份必须跨集群稳定，不能仅依赖 Pod 名称。
- 所有资源必须带有集群维度，避免跨集群同名资源混淆。

## 7. 产品信息架构

### 7.1 一级导航建议

1. **概览**：多集群健康主页。
2. **集群**：集群纳管、列表、详情和连接维护。
3. **事件**：Event 聚合、筛选和分析。
4. **巡检**：主动检查结果和问题清单。
5. **运维工具**：日志、Exec 等能力。
6. **AI 分析**：问题分析记录和建议。
7. **系统管理**：数据源、规则、凭据和审计。

未上线的模块可以不显示，避免出现大量空菜单。

### 7.2 三条核心导航主线

#### 集群主线

```text
全局概览 → 集群 → 节点/命名空间/工作负载/实例 → 资源详情
```

#### 业务主线

```text
全局搜索或业务全景入口 → 选择业务 → 跨集群分布 → 某集群中的工作负载/实例
```

#### 异常主线

```text
异常汇总 → 异常类型 → 受影响集群/业务 → Event、状态、指标或日志证据
```

## 8. 功能模块与优先级

### 8.1 优先级定义

- **P0**：构成平台最小可用闭环，优先实现。
- **P1**：支撑主要日常运维场景，P0 稳定后实施。
- **P2**：提高诊断与操作效率，需要前置能力成熟。
- **P3**：增强分析能力，不阻塞核心平台上线。

### 8.2 模块清单

| 编号 | 模块 | 优先级 | 核心范围 | 迭代说明 |
|---|---|---:|---|---|
| M01 | 集群管理 | P0 | 纳管、连接测试、列表、详情、更新凭据、移除、环境与标签 | 核心主线，最先建立基础能力 |
| M02 | 多集群健康概览 | P0 | 全局汇总、集群卡片/列表、异常高亮、刷新、下钻 | 首个用户可见功能，本文详细设计 |
| M03 | 集群资源查看 | P1 | 节点、命名空间、工作负载、实例只读查看 | 为下钻和诊断提供资源基础 |
| M04 | 业务跨集群全景 | P3（条件触发） | 业务识别、跨集群实例分布、版本与异常对比 | 当前无状态业务场景不实施；出现业务级影响面、版本/配置对比或 SLA 需求后再启动 |
| M05 | Event 管理 | P1 | Warning 聚合、去重、时间窗口、趋势、资源关联 | 不再仅保存原始 Event |
| M06 | 主动巡检 | P1 | 规则检查、周期任务、问题清单、历史变化 | 从被动告警转向主动发现 |
| M07 | 日志查看 | P2 | 容器日志、时间范围、实时跟随、大小限制 | Exec 的低风险前置能力 |
| M08 | 容器 Exec | P2 | 受控终端、PRD 二次确认、权限和审计 | 高风险能力，必须后置 |
| M09 | 指标与告警关联 | P2 | Prometheus 查询、关键趋势、Alertmanager 当前告警展示 | 复用现有系统，不在平台重复采集 |
| M10 | AI 分析 | P3 | 基于资源、Event、指标和历史问题生成摘要与建议 | 只分析和建议，第一阶段不自动执行操作 |

### Event、主动巡检与 AI 的职责边界

- **跨集群事件中心是事实层**：负责准实时 List + Watch、去重、归并、筛选、持久化和资源下钻，回答“发生了什么、发生在哪里、证据是什么”。
- **主动巡检是规则层**：周期读取集群状态、容量基线和关键指标，即使没有 Event 也能发现偏差，回答“当前是否违反已知稳定性规则”。
- **AI 巡检分析是解释层**：只消费事件小时聚合、巡检发现、容量变化、资源关系和少量原始样本，回答“可能原因、影响范围和建议先做什么”。
- AI 不建立第二条事件采集链路，不复制全量原始 Event，不替代确定性规则，也不直接执行变更。每条 AI 结论必须包含证据时间窗，并能下钻回事件或资源详情。

### 8.3 横切能力

以下能力不作为独立业务模块，但必须随相关模块同步建设：

- 单管理员登录，未来预留角色扩展。
- Kubernetes 凭据加密和轮换。
- 操作日志和危险操作审计。
- API 超时、限流和错误码。
- 平台自身日志、指标和健康检查。
- 数据备份和恢复。
- DEV/PRD 环境标识与防误操作。

### 8.4 推荐迭代顺序

```text
迭代 0：最小集群纳管能力
   ↓
迭代 1：多集群健康概览主页
   ↓
迭代 2：集群资源查看
   ↓
迭代 3：Event 管理
   ↓
迭代 4：主动巡检
   ↓
迭代 5：日志查看
   ↓
迭代 6：容器 Exec
   ↓
迭代 7：指标与告警关联
   ↓
迭代 8：AI 分析
   ↓
条件触发：业务跨集群全景
```

迭代 0 是主页可使用的技术前置，不追求完整集群管理体验；迭代 1 是第一个完整的用户可见功能。

## 9. 轻量化技术选型

### 9.1 选型原则

- 优先采用 Kubernetes 官方客户端和成熟基础组件。
- 第一阶段保持单体部署，减少服务发现、消息队列和分布式事务。
- 不把 Prometheus、Alertmanager 和日志系统已有数据复制进平台。
- 所有模块在代码和领域上隔离，但共享一个部署单元。
- 先满足约 60 套集群，再根据真实瓶颈扩展。

### 9.2 推荐技术栈

| 层次 | 推荐选型 | 选择理由 |
|---|---|---|
| Web 前端 | React + TypeScript + Material UI | 适合管理后台；Headlamp 采用相近技术；组件生态成熟 |
| 后端 | Go 模块化单体 | 与 Kubernetes 生态一致；并发和流式处理能力好；部署产物简单 |
| Kubernetes 访问 | 官方 `client-go` | 支持 Kubeconfig、List/Watch、日志和 Exec 等原生能力 |
| 平台数据 | SQLite 起步，保留 PostgreSQL 迁移能力 | 单实例初期轻量；出现高可用和多副本要求时迁移 PostgreSQL |
| 指标来源 | 复用现有 Prometheus | 不重复建设时序数据采集与存储 |
| 告警来源 | 复用现有 Alertmanager | 平台只读取和关联，第一阶段不负责发送通知 |
| 认证 | 第一阶段单管理员服务端会话 | 范围小、风险可控；未来再接 OIDC/企业身份 |
| 部署 | 单容器、单服务部署到管理集群 | 前后端同源，部署和排障简单 |
| AI | 可插拔模型适配层 | 避免绑定单一模型，并允许关闭 AI 模块 |

### 9.3 数据库取舍

#### 初始选择：SQLite

适用条件：

- 平台单实例运行。
- 用户数量少。
- 只保存平台配置、最新健康快照、少量历史和审计记录。
- 能接受通过备份恢复，而不是数据库自动高可用。

#### 升级条件：PostgreSQL

满足任一条件时进入迁移评估：

- 平台需要运行多个后端副本。
- 平台可用性要求提升，不能接受单点数据库。
- 健康历史、Event 聚合或审计数据明显增长。
- 出现复杂并发写入和查询需求。

不建议第一阶段引入 Redis、Kafka、Elasticsearch或独立时序数据库。只有真实需求出现后再增加。

### 9.4 不采用的方案

#### 直接 Fork Headlamp

Headlamp 适合作为交互和架构参考，但其插件、桌面端、通用资源操作等能力超出当前范围。直接 Fork 会增加跟随上游和裁剪功能的成本。

#### 一开始采用微服务

当前模块虽然较多，但由同一小团队按顺序开发，规模和流量不足以抵消服务拆分带来的部署、调用、追踪和数据一致性成本。

#### 每个集群部署 Agent

第一阶段直接通过 API Server 纳管，减少 60 套集群中的部署和升级工作。只有网络隔离、采集压力或本地诊断确实需要时，再评估可选 Agent。

## 10. 整体架构设计

### 10.1 架构风格

采用“中央控制面 + 模块化单体 + 按需访问多集群”的架构。

```text
┌──────────────────────────────────────────────────────┐
│                 浏览器 / React 前端                   │
│ 概览｜集群｜业务全景｜事件｜巡检｜运维工具｜系统管理 │
└──────────────────────────┬───────────────────────────┘
                           │ HTTPS / JSON / WebSocket
┌──────────────────────────▼───────────────────────────┐
│                    Go 模块化单体                     │
│                                                      │
│ API 与认证层                                         │
│ 集群管理｜健康聚合｜资源查询｜业务映射｜Event｜巡检  │
│ 日志与 Exec｜指标适配｜AI 分析｜审计                 │
│                                                      │
│ 集群客户端池｜刷新调度器｜快照缓存｜错误隔离         │
└──────────────┬───────────────────────┬───────────────┘
               │                       │
      ┌────────▼────────┐     ┌────────▼───────────────┐
      │ 平台数据库      │     │ 外部数据源             │
      │ 配置/快照/审计  │     │ Prometheus/Alertmanager│
      └─────────────────┘     └────────────────────────┘
               │
      ┌────────▼───────────────────────────────────────┐
      │ Kubernetes API Server × N                     │
      │ DEV 集群组 / PRD 集群组                       │
      └────────────────────────────────────────────────┘
```

### 10.2 架构分层

#### 展示层

- 提供统一导航、过滤、搜索、状态展示和下钻。
- 不保存 Kubernetes Token。
- 不直接访问各 Kubernetes API Server。
- 不在浏览器端完成跨集群聚合。

#### API 与安全层

- 处理登录、会话、输入校验和统一错误响应。
- 控制危险操作和环境提示。
- 对流式日志和 Exec 建立受控代理。
- 记录关键操作审计。

#### 领域模块层

- 集群管理是所有模块的基础。
- 健康聚合、资源查询、业务全景、Event 和巡检保持清晰边界。
- 模块之间通过内部接口协作，不允许直接随意读取其他模块的数据表。

#### 集群访问层

- 根据集群 ID 获取对应 Kubernetes 客户端。
- 管理连接超时、并发限制、客户端复用和凭据更新。
- 屏蔽不同 Kubernetes 版本差异。
- 单集群失败不得传播为全局失败。

#### 数据与缓存层

- 保存集群配置、加密凭据、业务映射、规则、最新健康快照和审计记录。
- 首页读取最新快照，不在每次页面打开时同步扇出查询全部集群。
- 高实时资源详情可按需查询 Kubernetes API。
- CPU、内存等指标按需查询 Prometheus，不长期复制原始时序数据。

### 10.3 三类数据时效

| 数据类型 | 示例 | 推荐获取方式 | 时效目标 |
|---|---|---|---|
| 平台配置 | 集群名称、环境、标签 | 数据库 | 修改后立即生效 |
| 健康快照 | 集群状态、节点与实例异常数 | 后台周期聚合 | 默认 60 秒以内 |
| 实时详情 | Pod 状态、日志、Exec | 按需访问集群 | 请求时实时获取 |
| 趋势指标 | CPU、内存、重启趋势 | 查询 Prometheus | 按查询时间范围获取 |

## 11. 主页：多集群健康概览详细设计

### 11.1 页面目标

主页不是传统监控大盘，而是多集群运维工作的入口。用户进入页面后应快速回答：

1. 当前有多少集群正常、警告、严重或不可达。
2. 哪些集群需要优先处理。
3. 异常主要来自节点、工作负载、实例、Event 还是连接问题。
4. 哪些业务受到影响。
5. 下一步应该进入哪里查看证据。

### 11.2 页面布局

```text
┌────────────────────────────────────────────────────────────┐
│ 标题 / 最后更新时间 / 自动刷新 / 手动刷新                  │
│ 环境筛选 / 状态筛选 / 标签筛选 / 搜索集群或业务            │
├────────────────────────────────────────────────────────────┤
│ 集群总数｜正常｜警告｜严重｜不可达｜异常节点｜异常实例      │
├────────────────────────────────────────────────────────────┤
│ 需要关注                                                     │
│ 严重问题、最近新增问题、受影响业务                          │
├────────────────────────────────────────────────────────────┤
│ 集群卡片视图 / 列表视图切换                                 │
│ [PRD-A] [PRD-B] [DEV-A] ...                                 │
├────────────────────────────────────────────────────────────┤
│ 业务全景入口：搜索业务 / 查看异常业务 / 查看全部业务         │
└────────────────────────────────────────────────────────────┘
```

### 11.3 顶部全局控制区

包含：

- 页面标题“多集群健康概览”。
- 数据最后完成聚合时间。
- 自动刷新开关和刷新周期提示。
- 手动刷新按钮。
- 环境筛选：全部、DEV、PRD。
- 状态筛选：正常、警告、严重、不可达。
- 集群标签筛选：机房、区域、用途等。
- 全局搜索：支持集群名称、命名空间和业务名称。
- 卡片视图与紧凑列表视图切换。

筛选只影响当前页面展示，不改变后台聚合范围。

### 11.4 全局汇总指标

第一行显示可操作的汇总数字：

| 指标 | 含义 | 点击行为 |
|---|---|---|
| 集群总数 | 当前纳管且未停用的集群数量 | 显示全部集群 |
| 正常集群 | 当前无已知关键异常 | 过滤正常集群 |
| 警告集群 | 可访问但存在需要关注的问题 | 过滤警告集群 |
| 严重集群 | 可访问但存在严重稳定性问题 | 过滤严重集群 |
| 不可达集群 | 网络、认证或 TLS 导致无法检查 | 过滤不可达集群 |
| 异常节点 | 非 Ready 或存在压力状态的节点总数 | 进入节点异常汇总 |
| 异常实例 | 非 Ready、异常状态或重启超阈值的实例总数 | 进入实例异常汇总 |
| 受影响业务 | 至少一个集群存在异常实例的业务数量 | 进入异常业务全景 |

不建议第一版只显示一个不可解释的健康分数。状态必须能够展开看到具体原因。

### 11.5 集群卡片展示维度

每张卡片必须包含：

#### 身份信息

- 集群名称。
- DEV/PRD 环境标识，PRD 使用更醒目的固定样式。
- 区域、机房或用途标签，可选显示。
- Kubernetes 版本。

#### 总体状态

- 正常、警告、严重、不可达四级状态。
- 状态产生的主要原因，最多展示 2～3 条。
- 最近成功检查时间。
- 数据过期时显示“数据已过期”，不能继续使用旧状态冒充当前状态。

#### 规模信息

- 节点：Ready 数 / 总数。
- 工作负载：正常数 / 总数。
- 实例：Ready 数 / 总数。
- 命名空间总数可放在详情或列表扩展列，不必占用卡片主视觉。

#### 异常信息

- 异常节点数。
- 异常工作负载数。
- 异常实例数。
- 最近时间窗口内 Warning Event 数。
- 重启次数超过阈值的实例数。

#### 关键指标

P0 不依赖 Prometheus 时：

- API Server 连通耗时。
- 节点 Ready 比例。
- 工作负载可用副本比例。
- 实例 Ready 比例。

接入 Prometheus 后增加：

- 集群 CPU 使用率和趋势。
- 集群内存使用率和趋势。
- 节点资源压力数量。
- 关键控制面指标，可配置显示。

指标数据源未接入时显示“指标未接入”，不显示 0。

#### 操作入口

- 查看集群详情。
- 查看异常资源。
- 查看该集群内的业务。
- 手动刷新此集群。

### 11.6 紧凑列表视图

当集群数量达到约 60 套时，列表视图应成为高效扫描方式。建议列包括：

- 状态。
- 环境。
- 集群名称。
- Kubernetes 版本。
- Ready 节点 / 总节点。
- Ready 实例 / 总实例。
- 异常节点。
- 异常工作负载。
- 异常实例。
- Warning Event。
- API 延迟。
- 最后检查时间。

默认排序顺序：不可达 → 严重 → 警告 → 正常；同状态内按异常数量和最近变化排序。

### 11.7 健康状态判定基线

#### 正常 Healthy

- API Server 可访问。
- 所有应检查节点 Ready。
- 没有达到严重阈值的节点压力。
- 工作负载可用副本满足期望。
- 没有达到阈值的异常实例或关键 Warning Event。

#### 警告 Warning

- 集群仍可访问。
- 存在少量非 Ready 实例、重复重启、短时副本不足或一般 Warning Event。
- 问题尚未达到严重阈值，但需要关注。

#### 严重 Critical

- 集群可访问，但存在节点大面积非 Ready、关键系统工作负载异常、大比例副本不可用等严重问题。
- 具体阈值在主动巡检模块中配置，主页只消费判定结果。

#### 不可达 Unreachable

- 网络连接超时或拒绝。
- Kubernetes Token 失效。
- TLS 校验失败。
- API Server 返回无法完成检查的错误。

不可达状态必须区分网络、认证、TLS 和未知错误，但只显示经过脱敏的错误原因。

### 11.8 异常高亮规则

- 颜色用于表达状态，不作为唯一表达方式；必须同时显示文字和图标。
- PRD 是环境属性，异常是健康属性，两者视觉表达不能混淆。
- 新出现的异常显示“新增”标识，并标记首次发现时间。
- 持续异常显示持续时长。
- 已恢复异常不继续占据当前异常区，可在历史记录中查看。
- 数据过期与集群不可达必须区分：过期表示没有新数据，不一定证明集群当前故障。
- 同一根因导致的大量实例异常应优先聚合，避免 100 个 Pod 生成 100 条首页问题。

### 11.9 聚合与刷新机制

#### 推荐机制

```text
后台刷新调度器
   ↓ 按集群并发受控地查询
各 Kubernetes API Server
   ↓
生成每个集群的健康快照
   ↓
保存最新快照和少量历史
   ↓
主页读取快照并定时轮询
```

#### 默认参数基线

- 后台每 60 秒刷新一次集群健康快照。
- 不同集群加入随机抖动，避免同一时间集中访问 60 套集群。
- 同时刷新集群数量默认限制在 5～10 个，可配置。
- 单集群检查设置独立超时，建议 5～10 秒。
- 浏览器每 30～60 秒获取一次聚合结果，不直接访问 Kubernetes。
- 手动刷新只触发指定集群或当前筛选范围，不阻塞页面。
- 手动刷新过程中继续显示旧快照，并标记“刷新中”。
- 超过两个刷新周期未成功更新的数据标记为过期。

#### 故障隔离

- 单集群超时只影响该集群快照。
- Prometheus 不可用时仍能展示 Kubernetes 原生状态。
- 数据库短时不可用时，已有内存快照可用于降级展示；写入失败需要记录平台告警。
- 聚合任务不得无限堆积；上一轮未完成时跳过或合并重复任务。

### 11.10 下钻路径

#### 从集群状态下钻

```text
主页集群卡片
  → 集群概览
    → 异常节点 / 异常工作负载 / 异常实例 / Event
      → 具体资源详情
        → 状态、Event、指标、日志，必要时进入 Exec
```

#### 从异常数字下钻

- 点击异常节点：进入该集群节点列表，并自动应用异常筛选。
- 点击异常工作负载：进入工作负载列表，并按不可用副本筛选。
- 点击异常实例：进入实例列表，并按异常类型筛选。
- 点击 Warning Event：进入 Event 页面，并保留集群和时间范围。

页面跳转必须保留来源上下文，用户能够返回原来的筛选条件。

### 11.11 业务全景入口

主页提供三个入口：

1. 顶部全局搜索可直接搜索业务名称。
2. “受影响业务”汇总数字进入异常业务列表。
3. 页面底部提供“查看全部业务”和“业务跨集群全景”入口。

从主页进入单业务全景后，至少看到：

- 该业务部署在哪些集群。
- 每个集群的期望实例、Ready 实例和异常实例。
- 不同集群使用的镜像版本。
- 最近重启、异常状态和 Warning Event。
- 每套集群最近一次数据更新时间。

业务全景的详细交互和聚合规则在 M04 模块设计中展开，本文只定义入口和最小展示要求。

### 11.12 空状态和异常状态

- 未纳管集群：引导进入集群管理并添加第一套集群。
- 正在首次采集：显示进度和已完成集群数量。
- 全部健康：明确显示“当前未发现异常”，同时保留集群列表。
- 部分数据源不可用：显示降级提示，保留仍然可信的数据。
- 全局聚合失败：显示最近成功快照时间，不能展示无时间信息的旧数据。

## 12. 非功能性需求

### 12.1 性能与规模

- 当前目标规模：约 60 套集群。
- 设计容量：至少 100 套集群。
- 首页读取已有快照的响应时间目标：P95 小于 3 秒。
- 单集群详情常规查询目标：P95 小于 5 秒，不包含日志和 Exec。
- 聚合刷新必须限制并发，不能对所有集群无控制扇出。

### 12.2 可用性与可靠性

- 平台属于内部运维工具，初始目标可用性为 99.5%。
- 单集群故障不得导致全局页面不可用。
- 最新快照必须携带采集时间和数据状态。
- 初始建议 RPO 不超过 24 小时，RTO 不超过 4 小时。
- SQLite 阶段至少每日备份，并验证恢复流程。

### 12.3 安全

- 平台与 Kubernetes API 全程使用 TLS。
- 不允许通过全局开关关闭 Kubernetes TLS 校验。
- Kubernetes Token、客户端证书和私钥使用独立密钥进行应用层加密。
- 管理员密码只保存安全哈希。
- 原始 Kubeconfig 不长期保存，不提供回看和下载。
- 前端不回显集群 Token、客户端证书或私钥。
- 日志禁止记录 Token、客户端证书、私钥、Kubeconfig、CA、Cookie 和完整敏感请求体。
- 所有写操作、凭据变更、移除集群和 Exec 都要记录审计。
- PRD 危险操作需要醒目标识和二次确认。
- AI 模块发送外部请求前必须进行字段最小化和敏感信息清理。

### 12.4 可维护性

- 模块化单体内部保持明确模块边界。
- 健康规则、刷新周期和阈值可配置，但提供安全默认值。
- 关键聚合和判定逻辑必须具有自动测试。
- 每个新模块开发前均需形成独立需求与设计文档。
- 平台升级应支持滚动或短暂停机升级，并提供回滚说明。

### 12.5 平台可观测性

平台自身至少暴露：

- HTTP 请求量、错误率和响应时间。
- 集群刷新成功率、失败原因和耗时。
- 待执行、执行中和超时的刷新任务数。
- 数据库错误和快照更新时间。
- 登录失败、凭据更新和 Exec 操作审计。

## 13. 主要故障模式与处理原则

| 故障 | 用户影响 | 处理原则 |
|---|---|---|
| 单集群 API 不可达 | 该集群显示不可达 | 其他集群继续刷新；展示脱敏原因和最后成功时间 |
| Token 失效 | 无法读取该集群 | 区分认证失败，引导更新 Kubeconfig |
| TLS 校验失败 | 无法安全连接 | 拒绝降级为不安全连接，引导更新 CA |
| Prometheus 不可用 | 无 CPU/内存指标 | 保留 Kubernetes 原生状态并标记指标不可用 |
| Alertmanager 不可用 | 无当前告警关联 | 不影响健康快照基础能力 |
| 数据库不可用 | 配置和快照写入失败 | 短时使用内存快照降级；禁止危险写操作 |
| 聚合任务超时 | 部分数据过期 | 独立超时、任务合并、限制并发、显示过期状态 |
| AI 服务不可用 | 无 AI 建议 | 不影响所有基础诊断和运维功能 |
| 平台重启 | 短时页面不可用 | 恢复集群配置，重新构建客户端并刷新快照 |

## 14. 关键架构决策记录

### ADR-001：采用模块化单体而非微服务

**状态：** 提议接受。

**决策：** 前端和 Go 后端作为一个产品交付，Go 后端内部按集群、健康、业务、Event、巡检等领域模块划分，初期单容器部署。

**理由：** 当前团队和规模适合顺序迭代；单体部署更轻，问题定位更直接。

**代价：** 各模块不能独立扩缩容；必须主动维护内部模块边界。

### ADR-002：采用中央控制面，不默认部署每集群 Agent

**状态：** 提议接受。

**决策：** 平台使用加密保存的 Kubeconfig 通过 API Server 访问所有集群。

**理由：** 减少约 60 套集群中的安装、升级和故障面。

**代价：** 平台必须具备访问各集群 API Server 的网络条件；网络隔离场景未来可能需要可选 Agent。

### ADR-003：首页基于后台健康快照，而非页面实时扇出

**状态：** 提议接受。

**决策：** 后台周期聚合每套集群的健康快照，首页读取已生成结果。

**理由：** 首页性能稳定，单集群超时不会拖慢全部页面，也能限制对 API Server 的访问压力。

**代价：** 首页数据存在最长约一个刷新周期的延迟，必须显示数据时间。

### ADR-004：平台不复制存储原始指标

**状态：** 提议接受。

**决策：** CPU、内存和趋势数据通过 Prometheus 查询；平台只保存必要摘要或引用。

**理由：** 避免重复建设采集、压缩、保留和查询系统。

**代价：** Prometheus 不可用时无法展示指标，但基础资源健康仍可工作。

### ADR-005：业务身份采用显式 Label，兼容名称推导

**状态：** 提议接受。

**决策：** 长期以 `business-id` Label 识别跨集群同一业务，第一版允许“命名空间 + 工作负载名称”回退。

**理由：** 显式身份稳定，能够支持一个业务包含多个工作负载；回退规则降低初期接入成本。

**代价：** 需要推动 Label 规范；回退规则可能出现同名误关联，页面必须标记识别方式。

## 15. 首个功能验收标准

多集群健康概览主页满足以下条件后，可认为迭代 1 完成：

1. 能展示所有已纳管集群，并支持 DEV/PRD 筛选。
2. 能展示正常、警告、严重、不可达四种状态及明确原因。
3. 每套集群展示节点和实例总数、Ready 数及异常数。
4. 能展示 Kubernetes 原生关键指标；Prometheus 未接入时正确显示“未接入”。
5. 全局汇总数字与集群卡片数据一致。
6. 单集群不可达时，其他集群正常展示和刷新。
7. 支持后台周期刷新、页面轮询、单集群手动刷新和数据过期提示。
8. 异常能够下钻到对应集群及异常资源入口。
9. 首页提供业务搜索和异常业务入口。
10. 所有数据均显示最近更新时间，旧数据不会冒充实时状态。
11. 页面、接口和日志不泄露 Kubernetes 凭据。
12. 约 60 套集群规模下，首页读取快照 P95 小于 3 秒。

## 17. 待评审事项

以下事项不阻塞本文档形成基线，但需要在对应模块设计前确认：

1. DEV/PRD 环境属性由人工录入、命名规则推导，还是从集群标签读取。
2. 第一版业务身份是否能推动统一 `business-id` Label，还是仅使用名称回退规则。
3. 哪些系统 Namespace 和关键工作负载需要纳入严重状态判断。
4. 节点、实例重启和副本不足的警告/严重阈值。
5. SQLite 阶段的备份位置、保留周期和恢复责任人。
6. 平台所在管理集群到全部 DEV/PRD API Server 的网络可达性。
7. PRD Exec 是否允许上线，以及所需审批、命令和审计边界。
8. Prometheus 是每集群独立部署还是存在统一查询入口，以及认证方式。
9. AI 数据是否允许发送到外部模型，允许发送的最小字段范围。
10. 平台初期是否继续采用单管理员，何时引入 OIDC 和多人角色。

## 18. 基线结论

平台以集群管理为核心，通过中央控制面统一纳管约 60 套 Kubernetes 集群。产品先建立集群和健康概览，再逐步扩展资源查看、业务全景、Event、主动巡检、日志、Exec、指标告警和 AI 分析。

技术上采用 React + TypeScript 前端、Go 模块化单体后端和官方 `client-go`，初期单容器部署并使用 SQLite，避免微服务、消息队列和每集群 Agent。主页依赖后台生成的健康快照，通过受控并发和错误隔离确保单集群故障不影响全局视图。

“业务”作为跨集群逻辑实体独立于 Namespace 和 Pod，以显式业务 Label 为长期身份、以“Namespace + 工作负载名称”为初期兼容规则，从而支持单业务跨集群全景视图。

本文档作为整体设计基线。后续从 M01 集群管理的最小纳管能力和 M02 多集群健康概览开始，逐个模块细化、开发和验收。
