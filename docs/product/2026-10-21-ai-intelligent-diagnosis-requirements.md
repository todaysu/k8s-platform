# FTC 集群运维平台—智能诊断与运营报告需求文档

- 版本：V1.0
- 日期：2026-10-21
- 状态：已暂停。2026-10-21 决定从当前产品与运行代码中移除 AI 分析模块，待需求重新确认后再重新建立基线。
- 关联文档：`ADR-0010 AI 分析从单集群症状复述改为证据链推理`

## 1. 文档目的

本文档定义 FTC 集群运维平台“智能诊断”的整体产品需求和实施优先级，作为后续功能详细设计、开发、测试和验收的共同基线。

本次需求覆盖：

1. Kubernetes 故障实时诊断。
2. Java 应用与 Arthas 受控自动诊断。
3. 诊断报告与上下文对话。
4. 集群历史事件周报、月报和季报。
5. 证据保存、操作审计、权限和安全边界。

本文档不展开具体代码实现。

## 2. 平台现状与问题

平台已具备集群健康、容量、Event、Workload、Pod、Node、Prometheus 趋势查询、Arthas 交互式终端和单集群 AI 分析的部分能力。

当前主要问题：

1. AI 主要复述“Pod 未就绪、重启次数高”等现象，缺少容器日志、完整 Node Condition、指标趋势等根因证据。
2. 分析以整个集群为范围，无法精确围绕 Pod、Workload、Event 或 Node 展开。
3. Arthas 主要是人工操作终端，还没有形成“自动取证—规则判断—AI 解释—报告保存”的闭环。
4. 历史 Event 虽已持久化和聚合，但尚未形成面向值班、治理和管理的周期性报告。
5. 目前一次分析结束后无法围绕已有证据追问。

## 3. 产品定位

智能诊断不定位为通用聊天机器人，而是平台内置的只读运维分析能力。

核心定位：

> 平台自动发现问题，运维人员决定是否启动诊断；平台先收集和验证证据，确定性规则优先判断，AI 仅用于复杂归因和自然语言解释。

平台最终需要回答：

1. 发生了什么？
2. 哪些集群、Namespace、Workload、Pod 或 Node 受影响？
3. 最可能的原因是什么？
4. 结论依据哪些真实证据？
5. 影响范围和严重程度如何？
6. 下一步应进行什么只读检查？
7. 相同问题是否曾发生、是否影响其他集群？

## 4. 目标与非目标

### 4.1 目标

1. 建立可复核的故障证据链。
2. 覆盖常见 Kubernetes 和 Java 运行时问题。
3. 所有诊断结论都能回溯到真实证据。
4. 用确定性规则降低 AI 误判和调用量。
5. 支持单次故障诊断、历史追问和周期运营报告。
6. 在 60+集群、单集群约200节点的目标规模下保持诊断任务可控。

### 4.2 非目标

1. 第一版不提供自动修复。
2. 不让 AI 自由生成并执行 kubectl、Shell 或 Arthas 命令。
3. 不自动执行 Heap Dump、Force GC、OGNL、JVM 参数修改等高风险操作。
4. 不将原始日志、Heap Dump 或业务敏感数据直接发给外部模型。
5. 不以 AI 自述的置信度作为运维决策依据。

## 5. 核心概念

### 5.1 待排查问题

由平台确定性逻辑自动产生，不调用 AI。问题至少包含：

- 问题类型和异常类别。
- 严重程度。
- 集群、环境、资源池、技术栈。
- 对象类型、Namespace、名称和 UID。
- 首次和最后出现时间。
- 问题指纹。
- 当前状态。

### 5.2 诊断任务

运维人员针对待排查问题或指定资源手动启动的一次受控分析。

状态流转：

```text
待诊断 → 排队中 → 采集证据 → 规则分析 → AI归因（可选） → 已完成
                                      └→ 证据不足
任意阶段 → 失败（保存已完成步骤和失败原因）
```

### 5.3 证据

诊断时从平台缓存、数据库、Kubernetes API、Prometheus 和受控 Arthas 会话中取得的可审核事实。

每条证据需要包含唯一编号、来源、采集时间、对象 UID、时间范围、截断标识和数据新鲜度。

### 5.4 诊断场景

由平台定义并经过测试的取证和判断流程。第一版提供预置场景，后续再支持管理员组合允许的步骤。

### 5.5 周期报告

由平台定时根据历史聚合事实生成的周报、月报或季报。统计结果由程序计算，AI 只负责解释趋势和生成治理建议。

## 6. 角色与权限

第一版仍为单管理员账号，但在数据和接口上预留以下操作权限：

1. 查看待排查问题和历史报告。
2. 启动普通只读诊断。
3. 启动受控 Arthas 诊断。
4. 确认高风险取证操作。
5. 配置诊断场景和报告调度。

所有诊断、取证、对话和确认操作都必须记录操作人和时间。

## 7. 功能信息架构

建议将现有“AI 分析”升级为一级菜单“智能分析”，包含：

1. **待排查**：平台自动发现的异常问题。
2. **实时诊断**：诊断任务、步骤、证据和结果。
3. **周期报告**：周报、月报和季报。
4. **历史记录**：已完成、失败、证据不足和已关闭诊断。

同时在集群概览、Workload、Pod、Event 和 Node 详情页提供“诊断此问题”入口，自动携带当前上下文。

## 8. 优先级与实施顺序

### 8.1 P0：共享诊断基础与安全边界

P0 是所有后续功能的前置，不单独作为客户功能发布。

#### P0-F01 诊断对象与任务模型

支持以下诊断范围：

- 集群。
- Workload。
- Pod。
- Node。
- Event 及其关联对象。
- 跨集群问题指纹（后续启用）。

诊断任务必须保存状态、目标、时间窗口、场景、操作人、步骤、失败原因和完成时间。

#### P0-F02 证据模型

证据类型至少包括：

- 集群健康快照。
- Event 与事件指纹。
- Workload、ReplicaSet、Pod 所有者链。
- Pod 容器当前状态、上一次退出状态、Reason 和 ExitCode。
- 当前容器日志和 previous 容器日志的有界摘要。
- Node 完整 Condition 和 taint。
- Prometheus 指标趋势。
- 容量与基线漂移。
- 安全扫描差异。
- Arthas 受控命令的结构化输出。

#### P0-F03 取证预算

- 按集群设置并发槽位。
- 按任务设置超时和最大远端请求数。
- 日志设置行数和总字节上限。
- Prometheus 设置时间范围、采样点和曲线数上限。
- 单个集群失败不阻塞其他集群。
- 证据被截断或部分缺失时必须显式标记。

#### P0-F04 安全与审计

- 所有命令必须来自服务端白名单模板。
- 禁止 AI 直接构造可执行命令。
- 证据进入模型前必须脱敏。
- 原始 Heap Dump 不进入 AI 模型。
- 操作人、目标、命令模板、开始时间、结束时间和结果必须审计。
- 第一版所有建议都是只读检查。

#### P0 验收条件

1. 任务能从排队到完成或失败正确流转。
2. 进程重启后可正确识别中断任务。
3. 每条结论可引用有效证据编号。
4. 超时、限流、权限不足和数据缺失都有明确状态，不得无限卡住。

### 8.2 P1：Kubernetes 实时诊断 V1

#### P1-F01 自动发现异常

平台自动识别并生成待排查问题，但不自动调用 AI。

第一版覆盖：

1. CrashLoopBackOff 和频繁重启。
2. OOMKilled。
3. ImagePullBackOff/ErrImagePull。
4. FailedScheduling。
5. 存活或就绪探针失败。
6. Node NotReady、MemoryPressure、DiskPressure、PIDPressure 和 NetworkUnavailable。

#### P1-F02 手动启动诊断

- 运维人员从待排查问题或资源详情页点击“开始智能诊断”。
- 弹窗显示目标集群、Namespace、资源、诊断场景和时间范围。
- 用户可填写“重点关注”，但不能通过文本注入执行命令。

#### P1-F03 分层判断

```text
收集基础证据
  → 执行确定性规则
    ├→ 规则命中且证据完整：直接形成结论
    └→ 规则未命中或存在冲突：调用 AI 归因
```

置信度由程序判定：

- `high`：确定性规则命中且必需证据完整。
- `medium`：证据支持某一方向，但未命中完整规则。
- `insufficient`：证据缺失、相互冲突或无法复核。

#### P1-F04 诊断过程展示

页面实时显示：

- 当前步骤。
- 已完成步骤。
- 正在采集的证据。
- 已耗时。
- 每个步骤的成功、跳过或失败状态。
- 失败原因和可重试建议。

#### P1-F05 诊断报告

报告至少包含：

1. 一句话结论。
2. 最可能原因。
3. 置信度。
4. 证据列表与原始页面链接。
5. 影响的 Namespace、Workload、Pod、Node 和集群。
6. 数据缺失与截断说明。
7. 下一步只读检查。
8. 规则版本、模型版本和诊断时间。

#### P1 验收条件

1. 预置六类故障都有可重复的测试数据和结果。
2. 已有规则可解释的问题不强制调用 AI。
3. AI 报告中不存在的证据引用会被拒绝。
4. 任务取消、超时或失败后不遗留后台运行操作。

### 8.3 P1：Java 内存受控自动诊断

本功能在 P0 完成后开发，可与 Kubernetes 诊断规则同批发布。

#### P1-J01 诊断发起

用户从 Java Workload 或 Pod 发起，指定：

- 目标应用或 Pod。
- 诊断场景“Java 内存持续增长”。
- 时间范围。
- 分析全部异常 Pod 或指定 Pod。
- 用户补充现象。

#### P1-J02 第一层：Kubernetes 与 Prometheus 证据

启动 Arthas 前先检查：

- 容器 Memory Working Set 趋势。
- Requests 和 Limit。
- 容器重启和 OOMKilled。
- 上一次退出原因和退出码。
- Node MemoryPressure。
- 应用内其他 Pod 的对比数据。
- 最近镜像或资源配置变化。

若已有证据可以确认容器 Limit 问题，可不启动 Arthas。

#### P1-J03 第二层：Arthas 运行条件检查

至少检查：

- 容器和 JVM 是否仍在运行。
- JDK/JRE 与 Arthas 兼容性。
- Arthas 是否能以 JVM 同一 UID Attach。
- `/tmp` 是否可写。
- 容器是否有足够的内存和磁盘空间进行低风险采集。

不满足条件时应显示原因并结束，不得长时间停留在“诊断中”。

#### P1-J04 第三层：低风险 Arthas 采集

第一版仅允许服务端白名单命令：

- `jvm`。
- `memory`。
- 限制次数和间隔的 `dashboard`。
- 有明确线程异常证据时，允许受限的 `thread`。

平台需要对多次采样结果做结构化解析，不只保存终端文本。

#### P1-J05 内存类型判断

诊断至少区分：

1. Java Heap/Old Gen 持续增长。
2. Direct Memory 增长。
3. Metaspace/ClassLoader 风险。
4. 线程数增长导致的 Native Stack 风险。
5. 容器 Limit 不足。
6. JVM Heap 下降但容器 RSS 不下降的堆外或 Native 风险。
7. 证据不足，需要更长时间观察。

#### P1-J06 会话清理

- 每次自动诊断使用独立 Arthas 会话标识。
- 完成、失败、取消、超时或用户离开时清理平台启动的 Arthas 会话。
- 不得终止业务 JVM。
- 清理失败需要形成审计告警。

#### P1-J07 高风险操作边界

以下操作不属于自动诊断：

- Heap Dump。
- `profiler alloc`。
- `vmtool heapAnalyze/referenceAnalyze`。
- `watch`、`trace`。
- 大范围对象实例查询。

若后续开放，必须作为独立操作、显示影响与预计耗时，并经运维人员二次确认。

以下操作第一版明确禁止自动执行：

- `forceGc`。
- 任意 `ognl`。
- 修改 `vmoption`。
- 修改系统属性或日志级别。
- `redefine` 和 `retransform`。

#### P1 Java 诊断验收条件

1. 可以从 Java Workload 或 Pod 发起诊断。
2. 能区分容器 Limit、Heap、Direct、Metaspace 和线程方向。
3. Arthas 无法 Attach 时在有界时间内失败并显示原因。
4. 自动诊断不会执行高风险或修改 JVM 状态的命令。
5. 任务结束后不遗留平台启动的 Arthas 进程。

### 8.4 P2：诊断上下文对话 V1

#### P2-F01 对话入口

- 对话作为已完成诊断报告的右侧抽屉。
- 不单独建设无上下文的通用聊天页。
- 对话与诊断任务、目标资源、证据版本绑定。

#### P2-F02 基于已有证据追问

第一版对话仅能使用已保存证据回答，不会因用户文本直接执行新命令。

建议快捷问题：

- 为什么判断是这个根因？
- 还有哪些可能性？
- 为什么不是另一类问题？
- 影响了哪些 Pod？
- 下一步应检查什么？
- 生成值班交接摘要。

#### P2-F03 引用与状态

- 每个回答必须引用有效证据。
- 没有证据时回答“当前证据不足”。
- 页面区分实时证据、历史快照和已失效对象。
- 对话记录与模型版本一起保存。

#### P2 验收条件

1. 用户可从报告页打开和收起对话抽屉。
2. 追问不会导致任意远程命令执行。
3. 对话答案无有效证据时不能伪装成确定结论。

### 8.5 P2：集群历史事件周报 V1

#### P2-R01 触发方式

- 每周自动生成上一自然周报告。
- 允许运维人员按时间范围手动生成或重新生成。
- 自动任务失败时保留统计事实，AI 失败不得导致整份报告不可用。

#### P2-R02 报告范围

第一版支持：

- 单集群。
- 全平台。

后续增加：

- 环境（ST/UAT/STP 等）。
- 资源池（G01/OCP）。
- 技术栈（TCS/CMBK8S/OCP）。

#### P2-R03 周报内容

1. Warning Event 发生次数和环比。
2. 受影响集群、Namespace、Workload、Pod 和 Node 数量。
3. Top 异常类别和问题指纹。
4. 新增问题、持续问题和已消失问题。
5. 问题集中的集群、业务 Namespace 和平台组件 Namespace。
6. 本周高置信度实时诊断结果。
7. 数据完整性、缺失集群和采集中断说明。
8. AI 生成的下周治理建议。

#### P2-R04 事实与 AI 边界

- 数量、排名、环比、趋势和影响范围必须由程序计算。
- 不向模型发送全量原始 Event。
- AI 仅接收结构化报告事实包，负责趋势解释和治理建议。
- AI 输出失败时仍显示完整统计报告。

#### P2 周报验收条件

1. 在 AI 关闭或调用失败时仍能生成周报。
2. 报告的数量和排名可与数据库聚合查询相互校验。
3. “无异常”与“无数据”明确区分。
4. 可从报告下钻到事件指纹、受影响集群和原始 Event。

### 8.6 P3：对话补充取证

在 P2 只读对话稳定后，允许对话提出补充取证建议。

支持的低风险操作：

- 继续采样指定时长。
- 扩大 Prometheus 时间窗口。
- 补采有界容器日志。
- 对比同一 Workload 的其他 Pod。
- 重新获取对象当前状态。

交互要求：

1. AI 先生成“补充取证提案”，不直接执行。
2. 页面显示目标、操作、时长、数据量和风险。
3. 用户确认后，后端将提案映射到服务端白名单步骤。
4. 新证据以新版本附加，不覆盖原诊断快照。

### 8.7 P3：月报、季报与多维度运营分析

#### P3-R01 月报

回答：

- 当月稳定性趋势是否改善。
- 哪些故障类型长期反复出现。
- 问题集中在哪个环境、资源池或技术栈。
- 哪些集群需要专项治理。
- 容量基线和安全基线是否恶化。

#### P3-R02 季报

回答：

- ST/UAT/STP 环境对比。
- G01 与 OCP 资源池对比。
- G01 内 TCS 与 CMBK8S 对比。
- 季度系统性风险。
- 重复问题的治理效果。
- 下季度优先治理清单。

#### P3-R03 报告对比与导出

- 支持与上一周期对比。
- 支持 Markdown 导出，后续增加 Word/PDF。
- 导出报告保留证据标识、数据窗口和完整性声明。

### 8.8 P4：后续评估能力

以下功能不进入当前开发计划：

1. 严重故障自动调用 AI 诊断。
2. 自动 Heap Dump 及自动下载。
3. AI 自主选择 Arthas/Kubernetes 工具。
4. 自动修复和自动执行变更。
5. 多智能体联邦或图数据库。

只有在规则准确率、证据完整率、任务资源消耗和审计能力达标后，才能单独评审。

## 9. 关键业务流程

### 9.1 实时故障诊断

```text
后台采集与规则检测
  → 自动生成待排查问题
  → 用户手动启动诊断
  → 限流与权限校验
  → 采集定点证据
  → 确定性规则判断
  → 必要时调用 AI
  → 校验证据引用
  → 保存报告和证据快照
```

### 9.2 Java 内存诊断

```text
用户选择 Java 应用
  → 检查 Kubernetes/Prometheus 证据
  → 选择异常 Pod
  → Arthas Attach 前置检查
  → 执行有界白名单采样
  → 区分 Heap/Direct/Metaspace/Thread/Limit
  → 形成证据报告
  → 停止平台启动的 Arthas 会话
```

### 9.3 报告追问

```text
用户提问
  → 加载本次诊断已保存证据
  ├→ 证据足够：引用证据回答
  └→ 证据不足：明确说明缺口
       └→ P3 后可生成补充取证提案，等待用户确认
```

### 9.4 周期报告

```text
原始 Event 和平台快照
  → 小时/日聚合
  → 程序计算排名、环比、趋势和影响面
  → 形成结构化报告事实包
  → AI 生成趋势解释与治理建议
  → 保存事实、AI 内容和数据完整性
```

## 10. 概念数据模型

后续详细设计应至少包含以下实体：

| 实体 | 用途 |
| --- | --- |
| `diagnostic_issue` | 平台自动发现的待排查问题 |
| `diagnostic_run` | 一次诊断任务及状态 |
| `diagnostic_step` | 诊断步骤、进度和失败原因 |
| `diagnostic_evidence` | 脱敏后的证据快照与版本 |
| `diagnostic_finding` | 确定性规则命中结果 |
| `diagnostic_report` | 结论、影响、置信度和建议 |
| `diagnostic_message` | 与某次诊断绑定的追问记录 |
| `periodic_report` | 周报、月报、季报状态与内容 |
| `periodic_report_facts` | 生成报告的结构化事实快照 |
| `diagnostic_audit` | 启动、确认、取消和命令模板审计 |

不引入图数据库；Kubernetes OwnerReference 在取证阶段构建有界依赖链。

## 11. 数据保留建议

### 11.1 Event 和周期报告

- Normal 原始 Event：7 天。
- Warning/异常原始 Event：30 天。
- Event 小时聚合：保持当前 365 天政策，容量压测后可调整。
- Event 日聚合：从 31 天扩展到至少 400 天。
- 已生成周期报告及事实快照：建议保留 24 个月。

### 11.2 实时诊断

以下周期需结合招商银行数据分级与合规要求最终确认：

- 诊断任务和报告：建议 12 个月。
- 脱敏后证据摘要：建议 12 个月。
- 容器日志摘要：建议 30 天。
- 诊断对话：建议 180 天。
- Heap Dump 等大文件：不纳入平台常规数据库，需单独审批和保留策略。

## 12. 非功能需求

### 12.1 性能与容量

1. 所有分析任务使用持久化有界队列。
2. 实时诊断与常规页面查询使用独立执行槽位。
3. 定时报告基于数据库聚合，不在生成报告时遍历 60+集群进行实时取证。
4. 单集群诊断不得触发其他集群全量采集。
5. 队列满、配额耗尽和模型不可用时需返回明确状态。

### 12.2 可靠性

1. AI 不可用时，规则诊断和统计报告仍可使用。
2. 平台重启后，未完成任务必须显示中断或可恢复状态。
3. 单数据源失败时保留其他有效证据，不将缺失视为正常。
4. 历史对象已删除或 UID 变化时，保留历史证据并标注对象已替换。

### 12.3 安全

1. 容器日志、Arthas 输出和对话内容进入模型前必须执行敏感信息脱敏。
2. 需要覆盖 Token、Password、Secret、Authorization、API Key，并根据客户要求评估手机号、身份证号、账号和订单号。
3. 数据库不保存未经管控的完整业务日志。
4. 所有可执行操作在服务端再次校验，不信任前端传入的命令。

### 12.4 可观测性

至少提供：

- 诊断队列长度。
- 各阶段耗时。
- 规则命中率。
- AI 调用量、错误率和超时数。
- 证据缺失率。
- Arthas Attach 成功率和清理失败数。
- 周期报告生成成功率。

## 13. 用户界面需求

### 13.1 待排查列表

展示：

- 问题摘要。
- 严重程度。
- 涉及集群和资源。
- 首次/最后发生时间。
- 发生次数。
- 是否已诊断。
- “开始诊断”入口。

### 13.2 诊断详情

页面顺序：

1. 目标与异常摘要。
2. 执行进度。
3. 诊断结论。
4. 置信度与数据完整性。
5. 证据链。
6. 影响范围。
7. 下一步只读检查。
8. 历史诊断对比。
9. 右侧追问抽屉。

### 13.3 Java 内存诊断视图

展示：

- 容器 Memory Working Set 与 Limit。
- Heap、Old Gen、Direct、Metaspace 和线程数趋势。
- GC 次数和回收效果。
- 同一 Workload 其他 Pod 对比。
- 最可能内存类型。
- Arthas 采样步骤和清理状态。

### 13.4 周期报告页

顶部筛选：

- 报告类型。
- 报告周期。
- 范围。
- 环境。
- 资源池。
- 技术栈。
- 集群。

主要内容：

1. 总体结论。
2. 异常趋势。
3. 影响范围。
4. Top 异常。
5. 新增、持续和已改善问题。
6. 容量与安全基线变化。
7. AI 治理建议。
8. 数据完整性说明。

## 14. 验收指标

功能实施后至少跟踪：

1. 常见故障规则覆盖率。
2. 规则诊断与人工确认一致率。
3. AI 结论具有有效证据引用的比例。
4. 证据不足但被误标为高置信度的次数。
5. 平均诊断时间和 P95 耗时。
6. 单次诊断远端 API 请求数和证据字节数。
7. AI 兜底调用比例。
8. Arthas 会话残留数，目标为 0。
9. 周期报告与数据库事实校验一致率。
10. 用户反馈：正确、部分正确、不正确。

## 15. 里程碑建议

| 里程碑 | 交付内容 | 优先级 |
| --- | --- | --- |
| M0 | 任务、证据、规则、限流、脱敏和审计基础 | P0 |
| M1 | Kubernetes 常见故障实时诊断闭环 | P1 |
| M2 | Java 内存受控 Arthas 自动诊断 | P1 |
| M3 | 基于已有证据的报告追问 | P2 |
| M4 | 单集群与全平台事件周报 | P2 |
| M5 | 经确认的补充取证 | P3 |
| M6 | 月报、季报、环境/资源池/技术栈对比 | P3 |

## 16. 待确认项

1. 招商银行对容器日志、AI 对话和诊断证据的最终保留期。
2. AI 模型是否部署在内网，以及哪些数据允许离开平台。
3. Java 内存诊断的默认采样时长、间隔和单集群并发上限。
4. 预置规则按 G01/OCP/TCS/CMBK8S 技术栈分化的范围。
5. 周报自动生成的具体时间、时区和失败通知方式。
6. 报告导出是否需要审批、水印和数据分级标记。

## 17. 优先级结论

必须严格遵循以下顺序：

```text
可信证据和安全基础
  → Kubernetes 实时诊断
  → Java 内存 Arthas 受控诊断
  → 基于已有证据的追问
  → 事件周报
  → 用户确认后的补充取证
  → 月报、季报和多集群治理分析
```

未建立证据和规则基础前，不优先开发通用对话界面；未建立权限、审计和任务资源限制前，不允许 AI 触发任何高风险操作。
