# FTC 集群运维平台功能说明

> 适用版本：v1.0.1
> 文档性质：面向使用者、实施与验收的功能说明。安装步骤见 [`../deployment/install.md`](../deployment/install.md)。

## 关于本指南

本指南按**运维能力**而非页面菜单组织内容。每个能力域回答四个问题：

| 小节 | 回答什么 |
| --- | --- |
| 解决什么问题 | 这个能力替代了哪些人工操作 |
| 关键概念 | 理解该能力必须掌握的对象与状态 |
| 使用流程 | 典型操作路径 |
| 数据来源与限制 | 数据从哪来、什么时候为空、边界在哪 |

**读者**：平台使用方（SRE/运维）、实施交付人员、验收方。

**约定**：文中「纳管集群」指已导入平台并被持续采集的 Kubernetes 集群；「联邦」指平台自身所管理集群的集合。命令示例以 `kubectl` 与 `curl` 为主。

## 1. 产品概述

### 1.1 定位

FTC 集群运维平台面向**多集群统一运维**场景，核心目标是缩短「发现问题 → 定位集群 → 判断影响」的路径。

与通用容器平台不同，它不承担应用发布、服务网格、CI/CD 编排职责，而是聚焦三件事：

1. **多集群状态的一致性视图** —— 避免逐套 `kubectl` 登录排查。
2. **问题证据的自动留存** —— 事件、扫描结果、容量基线可回溯对比。
3. **受控的高危操作入口** —— Exec、Arthas、kubectl 均有权限与审计约束。

适用场景：同一团队维护 5–100 套 Kubernetes 集群，需要值班巡检、故障定位、合规检查和周期性汇报。

不适用场景：单集群开发环境（直接使用 `kubectl` 更高效）、需要应用全生命周期管理的场景。

### 1.2 架构

平台自身部署在 Kubernetes 中，以 Web 服务形式提供，不要求客户端安装任何软件。

```
                    ┌─────────────────────────────┐
   浏览器 / HTTPS ──▶│  API 角色（无状态，可多副本） │
                    │  · 页面与 REST 接口          │
                    │  · 认证、鉴权、审计           │
                    └──────────┬──────────────────┘
                               │  读写快照 / 索引 / 聚合
                    ┌──────────▼──────────────────┐
                    │  MySQL 8.0+（外部依赖）       │
                    │  · 集群凭据（加密存储）       │
                    │  · 健康/容量快照、事件聚合    │
                    │  · 扫描报告、资源索引、告警   │
                    └──────────▲──────────────────┘
                               │
          ┌────────────────────┴────────────────────┐
          │                                         │
┌─────────┴──────────┐                  ┌───────────┴─────────┐
│  Collector 角色     │                  │  Worker 角色         │
│  · 健康快照 60s     │                  │  · 安全扫描 Job      │
│  · 容量采集         │                  │  · Arthas / 重型任务 │
│  · 事件 Watch       │                  │  · 长耗时导出        │
│  · 资源索引 10min   │                  │                     │
└─────────┬──────────┘                  └───────────┬─────────┘
          └──────────────┬──────────────────────────┘
                         ▼
              ┌────────────────────┐
              │  纳管集群（联邦）    │
              │  Kubernetes API     │
              └────────────────────┘
```

**角色拆分的意义**：三类负载的资源特征完全不同。API 请求要求低延迟、可水平扩展；Collector 是周期性批量任务，需要限制并发避免把纳管集群打满；Worker 执行分钟级甚至更长的任务，不能占用 API 的 Goroutine 与内存。混部时一次安全扫描就可能拖垮页面响应。

**文件与事件的读写边界（重要设计约束）**：

平台刻意避免「每次页面刷新都扇出访问所有集群」。集群列表、概览、容量、事件视图读取的都是数据库中的**快照与聚合结果**，只有三类操作会实时访问目标集群：

- 节点、工作负载、Pod 详情与日志、Exec（用户主动点击）
- 概览/容量的「显式刷新」按钮
- 资源索引为空时的兜底加载

这一约束决定了后续每个能力域的「数据来源」小节——**理解它，就能解释绝大多数「数据不实时」的疑问**。

### 1.3 能力矩阵

| 能力域 | 解决的问题 | 数据实时性 | 前置依赖 |
| --- | --- | --- | --- |
| 概览 | 全局健康态势一屏可见 | 快照（60s） | 无 |
| 集群管理 | 纳管集群并提供对象级操作 | 混合（快照 + 实时） | 目标集群 Kubeconfig |
| 监控 | 集群资源与容器指标趋势 | 实时查询 | 目标集群有 Prometheus |
| 告警 | 未恢复告警跨集群聚合 | 采集轮次 | 目标集群有 Alertmanager |
| 容量 | 资源池容量基线与漂移 | 快照 + 基线 | 完成集群分类 |
| 跨集群事件 | 事件检索与关联分析 | 采集 + 聚合 | 无 |
| 巡检分析 | 按规则自动生成问题清单 | 派生（基于快照） | 无 |
| 运行报告 | 周期汇报材料自动生成 | 快照 + 历史聚合 | 无（AI 总结可选） |
| 安全扫描 | CIS 基线 + 配置合规检查 | 手动触发 | kube-bench 镜像 |
| 运维工具 | 审计、JVM、Arthas、文件分发 | 按需 | 视工具而定 |

### 1.4 与 Red Hat ACM 的定位差异

前端采用与 ACM 相同的 PatternFly 6 设计体系，交互习惯接近，但能力边界不同：

| 维度 | Red Hat ACM | FTC 平台 |
| --- | --- | --- |
| 核心目标 | 应用跨云全生命周期（GitOps 驱动） | 集群稳定性、故障定位与合规留痕 |
| 应用管理 | 完整（Application Lifecycle、Subscription） | 不提供发布能力，只做运行时诊断 |
| 治理方式 | 策略即代码（Policy/Placement） | 扫描 + 白名单 + 差异对比 |
| 依赖组件 | 需安装 ACM Operator 与 Klusterlet | 仅需目标集群 Kubeconfig |
| 集群接入 | 通过 Klusterlet 双向连接 | 单向拉取，不需要在目标集群装 Agent |
| 规模定位 | 数百至数千集群 | 5–100 集群 |

**选择建议**：已经在用 OpenShift + ACM 的组织，FTC 平台可作为补充的「稳定性视图」使用，两者不冲突；未引入 ACM 的场景下，FTC 平台的接入成本更低（无需在目标集群部署任何组件）。

## 2. 核心概念

| 术语 | 含义 | 常见误解 |
| --- | --- | --- |
| **纳管** | 将集群 Kubeconfig 导入平台，由平台按周期采集 | 不等于获得该集群的写权限；平台默认只做只读采集 |
| **健康快照** | 平台定期采集的集群状态摘要，含节点/实例/组件就绪数、API 延迟 | 不是实时状态；页面上显示的「最后检查」才是采集时间 |
| **容量基线** | 平台对某集群资源池设定的期望区间，用于识别漂移 | 不是 K8s 的 ResourceQuota，是平台侧的管理概念 |
| **采集覆盖（Coverage）** | 单个集群某项采集是否成功、失败原因 | 面板为空不一定是 Bug，先看覆盖状态 |
| **事件聚合** | 将原始 Event 按小时/天/对象压缩存储 | 聚合后无法还原每一条原始事件的完整字段 |
| **白名单** | 经评审豁免的扫描项，不计入失败与得分 | 白名单不等于修复；记录豁免原因便于审计追溯 |
| **证据（Evidence）** | 巡检/告警结论所依据的具体数值与对象 | 证据随快照变化，历史证据需看报告快照 |

## 3. 能力域详解

### 3.1 概览

**解决什么问题**
值班交接时，需要一个页面回答「今天有没有集群不正常」。逐套登录 `kubectl get nodes` 在 20 套以上集群时不可行。

**关键概念**
- **健康状态三态**：`healthy` / `warning` / `unreachable`。
- **不可达不等于故障**：凭据过期、网络策略阻断、API Server 重启都会表现为 `unreachable`，需结合「最后检查时间」判断。
- **实例数来源可切换**：配置 `HEALTH_INSTANCE_SOURCE=workloads` 后，实例数来自 Deployment/StatefulSet/DaemonSet 的期望副本，健康采集只列 `kube-system` Pod。这是为避免每分钟全量读取业务 Pod 造成 API 压力。

**使用流程**
1. 打开「概览」，读取集群健康分布与告警计数。
2. 对 `warning`/`unreachable` 的集群，点击进入集群详情查看节点与组件状态。
3. 需要最新数据时点击「刷新」，该操作会实时访问目标集群，有并发上限。

**数据来源与限制**
- 数据来源：数据库中的健康快照，由 Collector 每 60 秒错峰刷新一轮，默认最多 5 套并发、单集群超时 20 秒。
- **某套集群采集失败不会清零历史数据**，而是保留上次成功指标并将该集群标记为连接失败——这一行为是有意的，避免偶发抖动造成大面积「未知」。
- 60 套集群建议先保持 `1m / 5 / 20s`，压测后再提高并发。
- 调整项：`HEALTH_COLLECTION_INTERVAL`、`HEALTH_COLLECTION_WORKERS`、`HEALTH_COLLECTION_TIMEOUT`，或「平台参数 → 采集」。

### 3.2 集群管理

**解决什么问题**
在统一入口下完成集群纳管、节点与工作负载查看、Pod 诊断（日志/Exec），无需在本地维护一堆 kubeconfig context。

**关键概念**
- **凭据加密**：Kubeconfig 使用 `CREDENTIAL_ENCRYPTION_KEY` 派生的密钥加密后存库，页面不回显明文。
- **连接校验**：纳管时先执行 `POST /api/v1/clusters/validate`，验证 API 可达与权限，通过后才入库。
- **权限最小化**：平台所需权限随功能递增——只读采集只需 `get/list/watch`；Exec 与 Arthas 需要 `pods/exec`；安全扫描需要创建 Job 的权限。权限不足时对应功能返回 `MONITORING_FORBIDDEN` 类错误，而不是静默失败。
- **kubectl 通道**：页面内 kubectl 与 TTY 走 WebSocket，受 `ENABLE_POD_EXEC` 与并发配额双重控制。

**使用流程**
1. 「集群 → 纳管集群」，填写名称并上传 Kubeconfig，先「校验」再保存。
2. 保存后等待 1 个采集周期（约 60 秒），概览与列表才会出现数据。
3. 进入集群详情可查看节点、工作负载；对 Pod 可查看日志、进入 Exec。

**数据来源与限制**
- 节点、工作负载、Pod 日志与 Exec 为**实时访问**，受目标集群 API 性能与网络影响。
- 集群详情中的健康摘要来自快照，可能落后最多 60 秒。
- Pod Exec 默认开启，可通过 `ENABLE_POD_EXEC=false` 全局关闭。
- 删除集群只删除平台侧记录与凭据，**不会影响目标集群本身**。

### 3.3 监控

**解决什么问题**
定位「某个 Pod 为什么突然变慢」时，需要在同一页面看到历史 CPU/内存/磁盘趋势，而不是跳到另一套 Grafana 找面板。

**关键概念**
- **自动发现数据源**：平台扫描纳管集群的 Service，满足以下条件即视为 Prometheus：
  - `命名空间 + 名称 + labels[app] + labels[app.kubernetes.io/name]` 拼接后包含 `prometheus`
  - 端口为 `9090`，或端口名包含 `web` / `http`
- **发现优先级**：名称含 `prometheus`（+10）> 命名空间含 `monitoring`（+5）> 端口 9090（+3）。同集群存在多个候选时取最高分。
- **查询方式**：通过 `services/proxy` 子资源转发到 Prometheus 的 `/api/v1/query`，**不要求 Prometheus 对外暴露**。
- **数据源固定**：单个请求内只使用一个数据源，避免不同面板混用两台 Prometheus 的数据。

**使用流程**
1. 进入「监控」，选择集群与时间范围。
2. 切换视图查看不同层面：
   - **总览**：Pod CPU/内存总量、APIServer 5xx、etcd Leader。
   - **节点性能**：主机级 CPU、负载、内存、磁盘空间、磁盘 I/O、网络收发与错误（11 个面板）。面板按「资源水位 / 磁盘 I/O / 网络」分组；节点多于一个时提供按主机筛选，选中后只显示该主机曲线。筛选在浏览器内完成，切换节点不会重新查询历史。
   - **Pod 资源**：按 Pod 查看 CPU、内存、磁盘吞吐与 IOPS，可按命名空间与 Pod 缩小范围。
   - **API Server**：请求速率、5xx 比例、P99 延迟、在途请求、429 限流。
   - **etcd**：Leader 可见性、切换速率、失败提案、WAL fsync 与后端提交延迟、DB 配额。
3. 面板无数据时先看提示信息：`MONITORING_NOT_CONFIGURED` 表示未发现 Prometheus，`MONITORING_FORBIDDEN` 表示凭据缺少 `services/proxy` 权限。

**节点性能视图的判定口径**

| 面板 | 口径 | 需要注意 |
| --- | --- | --- |
| CPU 使用率 | 各核非 idle 占比的节点平均 | 与「Pod 资源」的 CPU 之和不相等，差值来自系统进程 |
| 1 分钟负载 | `node_load1` | 含不可中断 I/O 等待；需结合核心数解读 |
| 内存使用率 | 基于 `MemAvailable` | 已计入可回收缓存，比 `free` 更接近真实压力 |
| 磁盘空间使用率 | 排除 tmpfs/overlay 等虚拟文件系统后按节点合计 | 单分区环境即根分区使用率 |
| 磁盘 I/O | 吞吐、IOPS、忙碌时间占比 | 多盘软 RAID 会相互掩盖，需结合 IOPS 判断 |
| 网络 | 排除回环与 CNI 虚拟设备后的收发速率 | 不排除会把 Pod 间流量重复计入物理网卡 |

曲线标签优先显示节点名，依赖采集配置注入 `node` 标签；未注入时回退显示采集地址。

**数据来源与限制**
- **强依赖目标集群已有 Prometheus**。平台不内置 Prometheus，也不代为部署。
- 所需指标来自三类采集目标：

| 指标类别 | 关键指标 | 采集来源 |
| --- | --- | --- |
| 容器资源 | `container_cpu_usage_seconds_total`、`container_memory_working_set_bytes`、`container_fs_*` | kubelet `/metrics/cadvisor` |
| 控制面 | `apiserver_request_*`、`apiserver_current_inflight_requests` | apiserver `/metrics` |
| etcd | `etcd_server_has_leader`、`etcd_mvcc_db_total_size_in_bytes`、`etcd_disk_*` | etcd `/metrics`（需 mTLS 客户端证书） |

- **etcd 指标缺失是常见情况**：etcd 默认只监听回环与节点 IP 且要求客户端证书，未配置证书时该面板永久为空，属预期行为而非缺陷。
- 指标保留时长由目标 Prometheus 决定，与平台无关。
- 仓库提供 `deploy/monitoring/manifests.yaml` 与 `scripts/setup-monitoring.sh`，可按需部署一套对齐上述要求的 Prometheus + Alertmanager。

### 3.4 告警

**解决什么问题**
Prometheus 的告警分散在各集群的 Alertmanager 中，值班人员需要逐个打开。平台将未恢复告警聚合到一处，并保留「哪个集群采集失败」的信息。

**关键概念**
- **发现规则**：与监控类似，扫描 Service 定位 Alertmanager，名称/标签含 `alertmanager` 即视为候选。
- **采集内容**：通过 `services/proxy` 读取 `/api/v2/alerts`，提取 `alertname`、`severity`、`namespace`、`pod`、`node`、`instance`、`deployment` 等标签。
- **指纹去重**：同一告警在不同采集轮次用 Fingerprint 识别，避免重复计数。
- **采集覆盖状态（Coverage）**：每个集群单独记录 `status` / `collected_at` / `message`。这是本功能最重要的设计——**「某个集群没有告警」和「某个集群采集失败」在页面上必须可区分**，否则会造成「一切正常」的误判。
- **单次上限**：单集群单次采集最多 5000 条，超出则报错，避免超大响应拖垮 API。

**使用流程**
1. 进入「告警」，默认展示所有集群的未恢复告警。
2. 按严重级别、状态、命名空间、时间范围筛选。
3. 查看「采集失败」标记的集群，进入该集群检查 Alertmanager 是否可达。
4. 定位到具体资源后，跳转集群详情或事件页查看上下文。

**数据来源与限制**
- 依赖目标集群已有 Alertmanager，且平台凭据具备 `services/proxy` 权限。
- 未发现 Alertmanager 时返回 `ALERTMANAGER_NOT_FOUND`，页面显示为「采集失败」而非「无告警」。
- 告警状态以 Alertmanager 为准，平台不做二次判定；告警解决后需等待 Alertmanager 停止上报才会消失。
- 保留天数由平台参数决定，超期记录会被清理。

### 3.5 容量

**解决什么问题**
回答「资源池还剩多少可用」「哪套集群偏离了既定容量规划」。这是资源申请与扩容评审的依据。

**关键概念**
- **分类维度**：集群按 **环境** 与 **技术栈** 分类，并归属到 **资源池**（如 G01、OCP）。未分类集群无法参与容量统计。
- **容量基线**：平台为集群设定的期望容量区间，可手动确认基线决策。
- **基线漂移**：实际容量变化超出基线允许范围，会在巡检中产生 `rebaseline` 提示。
- **可分配容量**：源自节点 `allocatable` 与已分配 request 的差值，不是节点物理容量。

**使用流程**
1. 「容量 → 分类」为集群设置环境、技术栈与资源池。
2. 查看全局容量视图，按资源池聚合 CPU/内存的申请率与可分配余量。
3. 对偏离基线的集群，查看漂移证据后决定「接受新基线」或「排查原因」。

**数据来源与限制**
- 容量数据来自 Collector 的容量快照，非实时；需最新值时使用显式刷新。
- **未分类集群不出现在容量统计中**，这是「容量页数字比预期少」的首要原因。
- 容量基于 request 而非实际用量（usage），两者差异大时需要结合监控页判断真实水位。
- 调整项：`CAPACITY_COLLECTION_INTERVAL`、`CAPACITY_COLLECTION_TIMEOUT`、`CAPACITY_COLLECTION_WORKERS`。

### 3.6 跨集群事件

**解决什么问题**
故障复盘时，需要跨集群检索「某时间段内所有 Warning 事件」，并关联到具体对象。逐集群 `kubectl get events` 无法聚合。

**关键概念**
- **非侵入式采集**：通过 Kubernetes API 的 `List + Watch` 获取事件，不在目标集群部署组件。
- **按 UID 去重并累加重复次数**，避免同一事件被反复插入。
- **三级保留策略**：

| 数据形态 | 保留期 | 用途 |
| --- | --- | --- |
| Normal 事件 | 7 天 | 近期变更追溯 |
| Warning 事件 | 30 天 | 故障复盘主力数据 |
| 小时聚合 | 365 天 | 长周期趋势与报告 |
| 日聚合 | 31 天 | 24 小时以上窗口的快速查询 |

- **查询降级策略**：24 小时以上时间窗口优先读取日/小时聚合，不再扫描原始事件——这是保证大时间跨度查询可用的关键。

**使用流程**
1. 进入「跨集群事件」，选择时间范围与集群。
2. 使用「问题视图」看聚合结论，「对象视图」看单个资源的事件序列。
3. 需要单条证据时下钻到原始事件。

**数据来源与限制**
- 事件由 Collector 持续 Watch，**平台停机期间的事件可能永久缺失**（K8s 事件本身默认只保留 1 小时）。
- 聚合后无法还原每条原始事件的完整字段，需要完整字段时必须在保留期内查询。
- 跨集群聚合在数据库内完成，只有单个资源的证据查询才会读取原始 Event。
- 调整项：事件保留天数与清理批量在「平台参数 → 事件」。

### 3.7 巡检分析

**解决什么问题**
把「健康快照 + 容量基线」中的异常转成一份可执行的待办清单，替代人工逐项比对。

**关键概念**
- **派生视图**：巡检结论由前端规则基于快照计算，不额外访问集群。因此**巡检的时效等于快照时效**。
- **六个分类**：可用性、节点、工作负载、容量、配置、监控。
- **三个级别**：严重、警告、提示。
- **结论来源**标注为「集群健康」或「容量基线」，每条结论包含 **证据（evidence）**、**解释（explanation）**、**建议（recommendation）**，可点击「查看容量证据」跳转到对应页面。

**内置规则（9 条）**

| 规则 | 触发条件 | 分类 |
| --- | --- | --- |
| 集群连接失败 | 健康状态为 `unreachable` | 可用性 |
| 实例未全部就绪 | 期望副本 ≠ 就绪副本 | 工作负载 |
| 指标数据不可用 | `metricsAvailable=false` | 监控 |
| 集群分类尚未完成 | 未设置环境/技术栈/资源池 | 配置 |
| 可分配容量偏低 | 余量低于阈值 | 容量 |
| 平台容量基线发生漂移 | 实际值超出基线区间 | 容量 |
| 业务 Pod 缺少资源申请 | 容器未设 requests | 工作负载 |
| 发现新的平台 Namespace | 出现未纳入基线的命名空间 | 配置 |
| 容量状态无法核验 | 容量快照缺失或过期 | 容量 |

**使用流程**
1. 进入「巡检分析」，按级别与分类筛选。
2. 逐条查看证据，确认是否真实问题。
3. 对确需处理项跳转对应页面操作；对可接受项记录原因（容量类可提交基线决策）。

**数据来源与限制**
- 完全依赖健康快照与容量快照，**不会发现这两类数据之外的深层问题**（如镜像拉取失败的具体原因需看事件或 Pod 状态）。
- 规则在前端计算，调整阈值需要更新前端版本，不是平台参数。
- 「集群连接失败」会连带抑制该集群的其他规则结论，避免单点故障产生大量噪声。

### 3.8 运行报告

**解决什么问题**
周报、月报、季度汇报需要固定的容量、事件、安全数据。手工汇总 20 套集群数据通常需要数小时。

**关键概念**
- **周期**：自然周、自然月、自然季度（按自然日历切分，不是滚动窗口）。
- **数据边界**：只读取数据库中已保存的 Event 小时聚合、安全扫描记录，以及生成时最新的健康/容量快照，**不会同时请求所有纳管集群**。
- **AI 总结可选**：可配置内网 OpenAI Chat Completions 兼容接口生成文字总结；API Key 加密保存且不回显。**模型不可用时事实图表仍会生成**，只是缺少文字总结。
- **输出形态**：平台内独立 HTML 图表页，支持页内预览、新窗口打开、复制直达链接；访问仍需登录。

**使用流程**
1. 「运行报告 → 生成」，选择周期类型与时间。
2. 按环境与资源池筛选范围（如只看 G01 生产）。
3. 生成后预览 HTML，或复制链接发给同事。
4. 需要定期产出时，使用平台参数配置报告范围默认值。

**数据来源与限制**
- 报告是**某一时刻的快照**，不随底层数据变化而更新；需要最新数据需重新生成。
- 事件部分依赖小时聚合，**保留期外的报告会缺失事件章节**。
- AI 总结仅做文字归纳，不参与数据计算；数值错误应排查快照源数据而非模型。
- 报告页面链接含访问控制，转发给无平台账号的人员无法打开。

### 3.9 安全扫描

**解决什么问题**
CIS Benchmark 与集群配置合规检查通常需要逐集群跑 kube-bench 并人工比对结果。平台将其流程化，并支持两次扫描的差异对比与豁免管理。

**关键概念**
- **两类检查合并**：
  1. **节点侧 CIS 基线**：以临时 Job 方式在目标节点运行 kube-bench，结束后自动回收 Job。
  2. **集群侧只读 API 检查**：Pod 安全上下文、RBAC、Service 暴露面、NetworkPolicy。
- **双架构镜像**：需分别配置通用/x86_64/ARM64 的 kube-bench 镜像，平台按节点架构选择。私有仓库需提供 ImagePullSecret。
- **差异对比**：同一集群再次扫描时，页面对比最近两次**成功**结果，标注「整改成功」「未整改」「新增风险」。
- **白名单**：不合规项可按集群加入白名单并填写原因，豁免项不再计入失败数与得分。
- **扫描需要较高权限**：创建 Job、读取节点信息、列举 RBAC 资源。权限不足时扫描会在预检阶段失败。

**使用流程**
1. 管理员在「平台参数 → 安全扫描」配置 kube-bench 镜像（含双架构）、Namespace、并发与超时。
2. 进入「安全扫描」，选择一套或多套集群，点击执行。
3. 扫描完成后查看得分与不合规项；对确认为可接受的项加入白名单并写明原因。
4. 整改后再次扫描，查看差异对比确认整改生效。

**数据来源与限制**
- **手动触发，不会自动周期扫描**。
- kube-bench 镜像必须能被**所有被纳管集群**拉取，否则该集群扫描失败。
- 扫描 Job 运行在目标集群的 kube-system（可配置），需要目标集群有可用节点资源。
- 白名单不做技术校验，**依赖评审流程**；建议配合报告定期复查豁免项。
- 扫描结论反映扫描时刻状态，配置变更后需重新扫描。

### 3.10 运维工具

一级菜单「运维工具」下包含四类相对独立的工具，共同点是都面向**具体故障的深挖**而非全局视图。

#### 3.10.1 审计日志分析

**解决什么**：拿到一份 Kubernetes audit 日志，快速定位「谁在什么时候改了哪个资源、哪些请求失败」。

- **本地解析，不上传服务端**：日志在浏览器内解析，不落库、不出网。
- 支持按资源、操作者、动词（create/update/patch/delete）筛选，区分写操作与读操作。
- 支持导出筛选结果为文件。
- **限制**：日志需自行从 apiserver 采集；文件过大时浏览器内存受限；解析失败通常是日志被截断或格式非标准 JSON lines。

#### 3.10.2 JVM 内存分析

**解决什么**：Java 应用出现内存增长或 Full GC 频繁时，不需要登录容器即可判断方向。

- 导入 `jstat` 输出、`GC.heap_info`、类直方图、GC 日志，判断老年代增长趋势、Full GC 频率、对象滞留与堆外内存风险。
- **本地解析，无需安装组件**，不依赖目标容器出网。
- **限制**：分析质量取决于输入数据完整性；只有 jstat 时无法判断对象级别泄漏。

#### 3.10.3 Arthas 诊断

**解决什么**：不熟悉 Arthas 的运维人员，需要在不安装 Agent、不开放端口的前提下排查线程、内存、慢调用。

- **内置 Arthas 4.3.5 发行包**，随平台二进制分发，通过 Kubernetes Exec 传入目标容器，不依赖容器出网或新增 Service。
- **支持架构**：Linux x86_64 / ARM64。
- **目标要求**：JDK 8+、`sh`、`tar`、可写 `/tmp`，且与 JVM 同用户运行。
- **受控会话**：先选集群 → 命名空间 → Pod → 容器，确认风险后启动；内置故障向导与社区排障案例。
- **版本可升级**：管理员可配置内网 HTTP/HTTPS 完整 ZIP 地址、版本与 SHA-256，平台下载校验后经 Exec 传入。
- **限制**：需要 `pods/exec` 权限；部分 Arthas 命令对生产 JVM 有性能影响，向导中标注了风险等级；容器内无 shell 或只读根文件系统时不可用。

#### 3.10.4 HTTP 文件服务

**解决什么**：为集群任务和内部客户端提供稳定的文件下载地址，避免每次临时搭建传输通道。

- 上传工具包并填写名称、版本、用途，生成固定下载地址 `/downloads/<id>/<文件名>`。
- **内容以 SHA-256 记录**，下载时可校验一致性。
- **下载接口不要求浏览器会话**：便于被集群内 Job 或脚本直接拉取；上传与删除仍需管理员权限。
- **单文件上限可配置**：在「平台参数 → 运行时 → HTTP 文件服务单文件上限」调整，保存后自动滚动重启 API 实例生效。
- **限制**：
  - 文件内容存储在平台数据库中，**调大上限需同步确认 MySQL 的 `max_allowed_packet`**，否则写入失败。
  - 若通过 Ingress 访问，代理的 `proxy-body-size` 需不小于该上限（平台在初始化时按初始值生成，后续调整需同步更新 Ingress）。
  - 下载地址长期有效但**不等于公开**：知道链接即可下载，敏感文件不应上传。

## 4. 跨能力协作

单个故障的完整排查路径通常跨越多个能力域。以下为典型组合：

| 场景 | 路径 |
| --- | --- |
| 集群整体不可用 | 概览（`unreachable`）→ 集群详情（节点/组件）→ 事件（Warning 时间线）→ 巡检（关联结论） |
| Pod 频繁重启 | 概览（`warning`）→ 监控（CPU/内存趋势）→ 事件（OOMKilled 等）→ 运维工具（JVM/Arthas） |
| 容量告急 | 容量（池余量）→ 巡检（可分配容量偏低）→ 集群详情（节点可分配）→ 监控（实际用量） |
| 合规检查 | 安全扫描（执行）→ 白名单（豁免评审）→ 运行报告（季度汇报引用） |
| 值班交接 | 概览（全局）→ 告警（未恢复）→ 巡检（待办）→ 运行报告（周期总结） |

**关键设计含义**：这些能力共享同一套快照与时序数据，因此**在概览看到的问题，必然能在巡检中找到对应结论**；反之若巡检无结论而概览异常，通常意味着该异常尚未纳入规则或数据未采集成功。

## 5. 已知限制

以下边界为设计取舍，不是待修复缺陷：

1. **不内置 Prometheus / Alertmanager**。监控与告警依赖目标集群已有组件；缺失时对应页面显示明确的「未配置」而非假装正常。
2. **采集型数据不是实时的**。健康 60s、容量与资源索引更长周期。需要实时值时必须显式刷新或查看对象详情。
3. **不提供应用发布能力**。平台定位是运维视图与诊断，不是 CI/CD 或 GitOps 控制器。
4. **单副本存储限制**。SQLite 方案仅面向单副本第一阶段；生产多副本需使用共享 MySQL 并启用 Leader Election。
5. **事件可能缺失**。平台停机期间产生的事件受 K8s 事件 TTL（默认 1 小时）限制，恢复后无法补采。
6. **巡检规则不可在线调整**。规则在前端计算，阈值变更需发布新版本。
7. **安全扫描不自动执行**。避免占用目标集群资源与产生非计划负载。
8. **文件服务不提供访问控制粒度**。下载链接为「知道即可访问」，不适合存放敏感凭证。

## 6. 版本与兼容性

| 组件 | 版本要求 | 说明 |
| --- | --- | --- |
| Kubernetes（纳管集群） | 1.24+ | 依赖 `services/proxy` 与标准 Events API |
| Kubernetes（平台自身） | 1.24+ | 清单基于 v1.24 API |
| MySQL | 8.0 / 8.4 | 必需外部依赖，需支持 `utf8mb4` |
| 浏览器 | 现代 Chromium / Firefox / Safari | 依赖 WebSocket（Exec、TTY） |
| kube-bench | v0.16.0 建议 | 需按节点架构分别提供镜像 |

**平台自身角色所需权限**（按功能递增，可按最小化原则裁剪）：

| 功能 | 必需权限 |
| --- | --- |
| 健康/容量/索引采集 | `get/list/watch` on nodes、pods、deployments、statefulsets、daemonsets、namespaces |
| 事件采集 | `get/list/watch` on events |
| 监控/告警 | `get` on services，`get` on `services/proxy` |
| Pod 日志 | `get` on `pods/log` |
| Exec / Arthas / kubectl | `create` on `pods/exec` |
| 安全扫描 | `create/delete` on `jobs`、`get/list` on RBAC 与 NetworkPolicy |
