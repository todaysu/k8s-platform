# ADR-0009：100 集群与 10 人并发运维的承载架构

- 日期：2026-10-21
- 状态：承载核心改造已实现，100 endpoint／10 用户短时模拟通过；未通过完整生产承载验收
- 目标：稳定纳管 60+ 套集群，以 100 套为设计与验收规模，支持 10 人同时运维
- 关联：ADR-0002（健康快照）、ADR-0003（多副本与统一 MySQL）、ADR-0005（读路径聚合）、ADR-0006（资源索引）、ADR-0007（事件日聚合）、ADR-0008（实例口径）
- 本文取代此前以连接创建为主要瓶颈的分析版本。本文是目标设计，未标记为现状的能力均需实现和验证。

## 1. 需求与验收口径

用户目标是：100 套集群接入后，10 人同时打开平台执行运维，页面流畅、平台不因负载崩溃，单集群异常不拖垮全局。此目标不能只用首页 QPS 或空集群数量证明。

### 1.1 数据与使用规模

| 维度 | 验收基线 | 说明 |
| --- | --- | --- |
| 纳管集群 | 60 套常态，100 套验收 | 网络延迟、对象数量不要求均匀 |
| 每套集群 | 200 Node、6,000 Pod | 100 套合计 20,000 Node、600,000 Pod；这是沿用的容量假设，生产分布需要复核 |
| 工作负载 | 每集群 1,000 个 Deployment/StatefulSet/DaemonSet，2,000 个 ReplicaSet | 用于初始压测造数，不能用 Pod 数代替这些对象数 |
| Namespace | 每集群 100 个 | 纳入容量分类与快照响应体测试 |
| 并发用户 | 10 个独立登录会话 | 不等于 10 RPS；每人多个接口和图表请求必须计入 |
| 实时终端 | 同时 10 个会话 | kubectl/Pod Exec/Arthas 合计；与 10 用户负载同时运行 |
| 稳态 Event | 每集群每秒 1 次事件更新 | 100 套合计 100 次/秒；仅为起始预算，必须用现场数据校正 |
| Event 突发 | 10 套各 50 次/秒，其余保持稳态，持续 10 分钟 | 约 590 次/秒；独立验证队列、持久化和恢复能力 |
| 稳定性 | 常态混合负载持续 24 小时 | 短时接口测试不能替代内存与连接泄漏测试 |

### 1.2 性能与可用性目标

下表为待验收目标，不是测量结果。必须固定压测机、平台配额、MySQL 配额、网络和数据量，并报告 P50/P95/P99、错误率与排队时间。

| 项目 | 验收目标 |
| --- | --- |
| 首页、集群列表、单集群快照 | API P95 ≤ 1 秒，P99 ≤ 3 秒；浏览器首屏可用 P95 ≤ 3 秒 |
| 资源搜索、容量列表、跨集群问题摘要 | API P95 ≤ 2 秒，P99 ≤ 5 秒；采用固定分页和受限时间范围 |
| 单集群原始事件查询 | 默认 24 小时、分页，P95 ≤ 3 秒；超范围引导缩小条件，不执行无界扫描 |
| 监控图表 | 典型 1 小时查询 P95 ≤ 5 秒；每条远端查询硬超时 8 秒；首次加载允许分批呈现 |
| 终端 | 目标集群可达时，WebSocket 通道建立 P95 ≤ 3 秒；Arthas 包传输与 attach 单独统计，不套用此承诺 |
| 普通读接口错误率 | 正常混合负载下平台原因 5xx/超时 < 0.1%；预期权限拒绝独立统计 |
| 健康新鲜度 | 正常集群最近成功采集年龄 P95 ≤ 90 秒、P99 ≤ 120 秒 |
| 容量／索引新鲜度 | 正常集群分别 P95 ≤ 6 分钟／12 分钟 |
| 资源稳定性 | 无 OOM、无负载引起的非预期重启；队列与 goroutine 不持续增长；稳定负载下内存无持续上升趋势 |
| 余量 | 常态 CPU P95、内存峰值均不超过对应 limit 的 70%；突发时仍无 OOM |
| 单个 API 副本退出 | 剩余副本仍满足普通页面读 SLO；已有终端可以断开并明确提示重连，不承诺跨 Pod 迁移会话 |
| 单个采集副本退出 | 其他分片继续；受影响分片目标 60 秒内被接管，健康年龄目标不超过 180 秒 |

离线集群不适用“成功采集新鲜度”，但必须展示最后成功时间、最近失败时间和失败原因。不能把旧数据标为最新，也不能把采集失败转换成零资源或健康。

## 2. 对现状的核对

1. 目前四个采集器由同一 Leader 并行启动，各自有 worker；`collectors.Wait()` 是等待退出，不是串行执行。问题是采集集中于单 Pod，不能跨副本分担。
2. `clientset` 确实重复构造，但 client-go v0.32.13 内部对相同 TLS 配置缓存底层 Transport。不能推断每个请求都新建连接池或执行 TLS 握手。是否有额外握手、解码或分配瓶颈应通过 profile、连接指标和基准测试确认。
3. 健康、容量与索引已有周期内错峰；资源索引首次运行不做错峰。仍需治理跨任务叠加、首次接入与故障恢复风暴。
4. 当前健康默认 60 秒／5 worker／20 秒超时，容量 5 分钟／3 worker／45 秒超时，索引 10 分钟／2 worker／30 秒超时。默认配置不构成 100 集群承载证明。
5. 前端存在轮询：集群列表 30 秒、容量等页面 60 秒，监控可配置刷新。监控、日志、Exec 等实时访问与页面快照需分别计入负载。
6. 单集群容量仍可能全量读取全部容量快照；跨集群事件仍存在逐集群数据库查询；索引仍有 DELETE + INSERT 写放大。这些是需要优化的已知路径，但优先级由实际耗时与负载决定。

## 3. 架构决策：隔离三类工作

```text
10 个浏览器会话
       |
  Ingress / Service
       |
  API Deployment（2 副本，任一副本可承接全部 10 用户普通读负载）
       |-- 快照、索引、事件聚合 --> MySQL
       |-- 有限实时查询 --------> 选定集群 API Server / services/proxy
       |-- 有限 WebSocket -----> 选定 Pod / kubectl / Arthas

  Collector Deployment（2 副本，每副本可持有多个 shard）
       |-- 认领固定 shard 数据库租约与 epoch
       |-- 有界任务调度 --> 100 套集群 Kubernetes API / Prometheus proxy
       |-- 事件流 --> 有界批量持久化 --> MySQL

  Job Worker Deployment（1 副本起）
       |-- 有界安全扫描、审计大文件分析等重任务
       |-- 持久化任务状态 --> MySQL；大文件在持久化文件存储
```

### 3.1 部署与资源隔离

- API、Collector、Job Worker 使用同一项目构建产物，通过运行角色配置选择启动内容；不引入微服务 RPC。
- API Pod 不运行定时采集和扫描，Collector 不提供用户查询。Worker 不与交互 API 共用重任务执行槽。
- 角色显式配置、最小权限 RBAC、独立 requests/limits、独立就绪与存活检查。API 多副本打散到不同节点，配置滚动更新与 PDB；所在 Kubernetes 集群自身应有冗余。
- API 副本的会话与元数据依赖统一 MySQL，不依赖粘性会话。WebSocket 仍归当前 API Pod；Ingress 配置连接空闲超时与优雅下线。
- API、Collector、Worker 从统一 Secret 获取所需配置；同一角色的凭据读取／刷新机制一致。拆 Deployment 本身不要求新增凭据分发系统。
- MySQL 是共享故障域，生产使用可备份、可恢复且满足目标可用性的 MySQL 服务；两个 API 副本不能补偿单实例数据库失效。数据库不可用时 API 有界失败，采集停止扩张缓冲，恢复后受控补采。
- 大文件审计分析的流式上传、持久化文件存储和任务隔离另立专项设计；未完成前保留当前上传限制，不宣称已经支持多份 500 MB 文件。

### 3.2 读路径只做有界工作

- 概览、集群列表、容量、资源搜索只读平台数据库的摘要／索引；请求中禁止遍历所有目标集群。索引为空时返回“准备中”，不自动退回全局远端 List。
- 单集群详情、监控、日志和终端允许显式访问已选集群，须经过实时操作预算；缺少快照时返回 pending，不通过普通 GET 隐式触发远端采集。
- 单集群容量按 clusterID 读取；全局业务分类是全局查询，读取独立的必要摘要，不能加载全部大 JSON 明细再过滤。
- 跨集群问题摘要使用聚合表和集合 SQL，先筛选权限／集群／时间，再聚合；限制返回分组数，分页后返回。不能将所有原始事件读进 Go 再分页。
- 搜索默认 20 条、最大 100 条；原始 Event 默认 50 条、最大 200 条。高偏移场景采用稳定排序游标，避免深 OFFSET。
- 默认原始 Event 查询限定单集群、24 小时，允许的上限由压测确定；长期趋势读日／小时聚合，不能无界查 30 天原始数据。
- 为真实查询设计索引并检查 EXPLAIN；逐集群串行 SQL 不应简单改为 100 个并发 SQL，优先集合查询或预聚合。
- 对高频相同查询采用短 TTL 缓存和 singleflight；键必须包含用户可见范围、过滤条件、时间桶及数据版本。缓存有条数和字节上限；单进程合并不能宣称跨副本全局合并。
- 总览响应不携带全量 Pod／Namespace 明细。前端表格分页或虚拟化，图表按视口加载，不同时渲染 100 套集群全部曲线。

### 3.3 实时操作预算与前端调度

以下为全平台初始预算，须由压测调优。实施时通过数据库短租约／配额槽等跨副本方式分配，或给定部署规模下按副本严格拆分；不能每个副本都使用整个平台预算。

| 操作 | 全平台初始上限 | 单集群／单用户约束 |
| --- | --- | --- |
| 实时 Kubernetes 读请求 | 20 个在途 | 每集群 2 个；与采集预算合并计量 |
| Prometheus 查询 | 8 个在途 | 每集群 2 个；单用户最多 4 个图表请求在途 |
| kubectl／Pod Exec／Arthas | 10 个会话 | 单用户最多 2 个；设空闲及最长会话时间 |
| 安全扫描等重任务 | 2 个运行任务 | 同集群同类任务去重；队列有限，不能在 API 请求内同步执行 |

- 页面普通读和实时请求使用不同准入队列，重任务无法占用全部 API 处理槽；重操作队列满时快速返回 429/任务排队状态与重试提示。
- 健康轮询默认 30 秒，容量 60 秒；非可见标签页暂停，错误指数退避并加随机抖动，同一视图禁止前次未完成又启动下一次。
- 监控默认 30 秒刷新，仅查询当前集群；切换页面取消旧查询，限制时间跨度、曲线数、响应字节和点数。相同集群、面板、时间桶做短缓存；保留 services/proxy，不要求被纳管 Prometheus 对外暴露。
- CPU／内存等监控摘要可按 60～120 秒采集，与健康可达性分离；容量趋势用 5 分钟。快照分别保存各指标的采样时间。面板实时查询仍适用上述独立预算。
- 日志限制 tail、字节率和总输出；Exec 输出使用有界缓冲，慢浏览器不能使服务端无限存储。10 个浏览器同时运行终端必须纳入测试。
- 人工刷新、扫描触发和变更操作均去重、限速并审计；不能由前端刷新绕过采集预算。变更操作不自动重试。

## 4. 采集调度与故障隔离

### 4.1 分片与所有权

- 初始采用固定 16 个逻辑 shard，按 clusterID 稳定哈希分配。shard 数与副本数独立；单个 Collector 可以认领多个 shard，两副本均衡持有，单副本故障后存活副本可接管全部分片。
- 分片模式以共享 MySQL 作为唯一所有权来源，避免 Kubernetes Lease 与数据库 epoch 双源不同步。固定 16 shard，成员每 3 秒续租、租期 45 秒，按活跃成员均衡认领；同一集群的健康、容量、索引与 Event 归同一 owner。成员心跳独立于大数据事务，所有权变更递增 epoch。旧的单 Leader 模式仍使用 Kubernetes Lease。
- shard 数变更需要版本化映射和迁移流程，不能直接改取模造成新旧 owner 重叠。
- Lease 丢失必须取消该 shard 的请求、Watch、排队任务与持久化任务；数据库保存递增 ownership epoch，快照／索引提交必须验证 epoch。新 owner 激活时先推进 epoch，旧 owner 的迟到写入不得覆盖新结果。该检查与提交必须在同一事务中完成。
- Event 采用幂等键与版本／时间规则，旧事件不能倒写新状态；采集状态同样受 epoch 保护。持久化事务对 shard 所有权行持共享锁，并在提交前重新检查 owner、epoch 与成员租期；所有权变更必须等待正在提交的事务。全局保留清理由 shard 0 调度；删除操作不替代逐集群 fencing。
- 每个集群同类型任务最多一个执行实例，未结束时不重复排队；排队按最新需求合并，不逐轮积压。
- 健康优先于容量与索引。对慢集群使用独立超时、退避与下一次调度时间；不让一个超时任务阻塞整轮其他健康集群。

### 4.2 并发、吞吐与内存预算

吞吐必要条件：`集群数 × 平均任务耗时 / worker 数 < 周期`。它不能替代排队 P99、新鲜度与内存测量。

以 100 集群为例，原默认配置健康平均单集群耗时必须 < 3 秒、容量 < 9 秒、索引 < 12 秒，尚未计算抖动、持久化和故障恢复余量。

初始建议总预算：健康 12 个轻任务、容量和索引共享 4 个大 List 槽；每集群大 List 最多 1 个。此为两 Collector 合计，不是每副本配置。单副本接管后保持总预算不翻倍；每个 owner 同时执行的数量由其 shard 配额与实际资源上限共同约束。

- 逐集群调度，不等待全部集群完成才决定下一轮；周期附带抖动，冷启动和重新接入也要错峰。
- 连接复用、clientset 缓存及凭据解析缓存一起治理，但不以未经测量的 TLS 握手浪费作为容量依据。缓存区分凭据版本、读／Watch／流式用途；凭据轮换失效，Watch 不使用普通短请求的 http.Client.Timeout。
- client-go 自带的每客户端限流不等于平台全局限流。共享每集群令牌桶与并发槽，覆盖健康、容量、索引、监控和实时查询；必要时给 API 实时路径分配固定子预算，保证与 Collector 合计不超额。
- 大对象 List 在后端兼容性验证后分页读取，页大小初始 500；处理 continue token 与过期重启，不允许读取部分页后覆盖完整快照。ResourceVersion、分页、API Server 版本和 watch cache 的兼容行为必须做集成测试。
- 逐页提取最小字段，丢弃 managedFields 和无需保留的 spec/status；计算业务摘要需要完整遍历，但不需常驻全量原始对象。设置响应大小、对象数和任务内存保护；超限显示采集失败／超限，不静默截断并标成功。
- 容量与索引优先复用同一 owner 的短时 Pod 摘要批次，携带批次时间与完整性；不要为了去重引入 600,000 个完整 Pod 的中央缓存。
- 以单槽峰值解码内存估算总峰值：基础内存 + 大 List 槽数 × 单槽峰值 + Event 队列 + 写入缓冲。需要同时测网络字节、解码分配、GC 和 RSS。

### 4.3 Watch 的采用条件

Event 继续使用 List + Watch。Node 与工作负载增量缓存作为压测后的可选优化，而非 100 集群上线前无条件引入：

- 先测周期 List 是否消耗目标 API Server 或平台的不可接受资源，再对 Node／工作负载启用 Watch。
- 明确首次同步、断线重连、410 Gone 后重新 List、删除处理、凭据轮换、RBAC 缺失和 owner 切换。
- 缓存未同步／断连时保留最后成功快照并标 stale；不能把空缓存发布成零资源。
- 完整同步年龄、Watch 断连时长与写回时间分别监控。“一个 watch 同步周期以内”不能作为断网期间的新鲜度保证。

## 5. 存储与事件流

- 生产使用 MySQL；SQLite 只用于开发和功能测试，不用于证明多副本承载。
- API、Collector、Worker 使用独立连接池和数据库账号／预算。起始上限可为每 API 10、每 Collector 10、Worker 5，当前部署共 45 条连接；预留迁移、管理及故障排查连接，扩副本前重算总和。最终以 DB CPU、锁、IO 和连接等待验证，不直接增大 MaxOpenConns。
- 只读查询与写入事务设独立超时。事件批量写入初始每批最多 200 条或 1 秒提交；队列按条数与总字节双重限制，不能用无界 channel。
- Event 持久化失败时不推进已持久化水位。队列满则暂停读取／关闭 Watch，按最近已持久化水位恢复；RV 已过期时重做 List，并展示采集中断区间。Kubernetes Event 有 TTL，长时间故障可能无法补回，不能承诺零丢失。若业务要求完整审计，另用 audit 日志链路。
- Watch 只在持有 owner 的副本运行，重连指数退避并随机化；初始窗口按集群数和恢复 SLO 设定，不能机械增到 60 秒而忽略接管时间。
- 索引用 UID、内容摘要与采集代次做增量 upsert；完整批次成功后才清理旧代次，失败保留旧索引。ownership epoch 防止旧批次执行清理。资源删除与重建必须区分 UID。
- staging／generation 可保证切换完整性，但不自动减少写入；是否引入 staging 取决于实测锁竞争与查询一致性要求。
- 原始事件、聚合、资源索引和快照分别设保留／清理策略，分批执行，避免大事务清理阻塞页面。
- Event 保留成本按实际持久化方式测量：100 次更新/秒 × 30 天约 2.59 亿次更新，不等于 2.59 亿条记录；是否按 UID 更新、保存历史版本、索引和 binlog 都影响磁盘。现有 100 GiB 示例 PVC 不是容量保证。数据库容量预算必须有实际行宽、唯一事件数、写入速率、留存、备份和至少 30% 余量依据。

## 6. 初始部署预算与扩容门槛

以下是压测起点，非最低硬件承诺，也不表示加资源可以替代修复无界查询。生产资源以最终压测报告为准。

| 角色 | 初始副本 | 每副本 requests | 每副本 limits | 故障要求 |
| --- | --- | --- | --- | --- |
| API | 2 | 1 CPU / 1 GiB | 2 CPU / 2 GiB | 任一副本承接 10 用户普通读与限定实时操作 |
| Collector | 2 | 2 CPU / 2 GiB | 4 CPU / 4 GiB | 存活副本接管全部 shard 时满足故障 SLO |
| Job Worker | 1 | 1 CPU / 1 GiB | 2 CPU / 2 GiB | 独立有界任务；不得拖垮 API；任务可恢复 |
| MySQL | 生产数据库服务 | 初始 4 CPU / 8 GiB 等级 | 按实际部署定义 | SSD、备份、恢复验证；HA 配置另见部署方案 |

API 按请求延迟、CPU 与实时会话数扩容；Collector 按调度延迟、采集年龄、大 List 槽和内存扩容。不能只按 CPU 自动加副本，因为远端 API 与 MySQL 总预算不会随 Pod 数自动增加。若需要 HPA，必须先实现跨副本配额分配。

## 7. 压测与故障验收

### 7.1 测试环境与真实性

- 先用 60／100 个独立逻辑 API endpoint、独立数据和连接，验证中央控制面的调度、解码、存储与用户负载。把一个小集群重复纳管 100 次不能模拟 100 个大集群。
- 规模模拟器要支持真实体量对象、List 分页／错误、Watch、断连、RV 过期、延迟和限流；Prometheus 模拟器支持大序列响应和超时。
- 至少选一套接近 200 节点／6,000 Pod 的真实或等效集群，对比 API Server、Prometheus 和平台开销；模拟接口通过不等于真实 Kubernetes 压力验收通过。
- 报告注明模拟与实测部分、Kubernetes 版本、认证类型、网络 RTT、数据分布、平台／数据库资源、前端浏览器与版本。

### 7.2 混合用户场景

10 个独立用户同时在线：4 人浏览概览／容量并轮询，2 人搜索及查事件，2 人查看监控（各 8 面板），2 人查集群详情和日志；同时维持 10 个终端连接，以验证后台连接成本。另测 10 人同时打开监控、同时点击刷新、同一资源搜索与 10 人在浏览器执行操作，不能仅用 HTTP 压测代替浏览器渲染测试。

正常读接口先施加 20 RPS 混合负载并观测 SLO，再做 50 RPS、持续 5 分钟的短时突发。RPS 是安全余量场景，不把它当作 10 用户行为的精确换算；最终负载比例由页面请求录制校准。429／主动降级在突发中允许，但正常负载不能靠持续拒绝用户操作达标。

### 7.3 必测矩阵

1. 60 集群、10 用户稳定运行；100 集群、10 用户运行 24 小时。
2. 100 集群冷启动、同时接入、索引为空、凭据集中更新；普通读仍受保护。
3. 10% 集群超时／离线，另外集群正常；无整轮阻塞、无重试风暴。
4. Event 按 1.1 的突发模型持续 10 分钟，恢复后队列排空、积压不持续增长，记录恢复时间。
5. 慢 Prometheus、慢浏览器、日志大输出、并发 Arthas 离线包传输；普通页面 SLO 不退化。
6. 分别终止一个 API、一个 Collector；验证存活容量、WebSocket 提示、shard 接管、旧 owner 迟到写入被拒绝。
7. MySQL 慢查询／短时不可用／连接耗尽：内存与队列有界，恢复后受控补采；记录期间数据缺口与用户提示。
8. 大集群分布不均、Pod 高频创建删除、分页中断、Watch 410、权限拒绝、长查询取消、重复任务与原始事件保留清理。
9. 2 倍对象量作为超额保护测试：允许 stale／限流／任务拒绝，但不允许 OOM 和请求无界排队；不据此宣称已支持 200 集群。

### 7.4 观测与发布门槛

采集并保存：每接口延迟／错误／排队，浏览器首屏与长任务，Go CPU／RSS／heap／GC／goroutine／FD，远端每集群请求／字节／429／超时，任务采集年龄与调度延迟，shard owner／epoch，Event 队列条数／字节／水位／缺口，MySQL 连接等待／慢查询／锁／磁盘／binlog 与查询计划。

每阶段提交可复现压测脚本、造数参数、仪表或指标导出、结果报告与回滚开关。未满足 1.2 的项目逐项列出，不使用“优化完成”等同于“100 集群验收通过”。

## 8. 落地阶段

1. **测量与读路径治理**：补齐压测工具和指标；移除自动远端 fan-out 降级；单集群快照读取；事件集合查询／预聚合；分页与前端请求预算。先在现有单 Leader 上建立可信基线。
2. **资源隔离与有界执行**：增加运行角色，拆 API／Collector／Worker Deployment；客户端及限流预算统一；监控查询准入；大 List 内存保护；Event 有界批处理与失败恢复。
3. **分片与完整性**：固定 shard、多 shard 认领、epoch fencing、故障接管、索引完整批次与幂等。保留单 Collector 模式用于回滚；灰度时按集群迁移所有权，禁止旧新两套同时采集。
4. **60→100 验收**：混合用户、稳定性、故障、真实目标集群验证。依据瓶颈决定是否增加 Node／工作负载 Watch、资源与数据库索引，产出最终推荐部署配置。

每阶段只在前置结果达标后进入下一阶段，不预先把“1～2 周”作为解除容量上限的保证。安全扫描产品策略、异常入口与容量基线交互改进放入独立需求，不混入性能验收。

## 9. 取舍与暂不采用

- 保留非侵入式纳管，不要求被纳管集群安装 Agent，不要求 Prometheus 暴露外网 Service。
- 不中央常驻缓存 600,000 个完整 Pod；优先最小摘要、低频分页与可控并发。
- 初期不引入 Kafka／Redis。MySQL 租约 + 有界队列可先实现；若实测表明需要持久消息缓冲或跨副本缓存，再另立 ADR 比较运维成本与故障语义。
- 接受快照延迟与故障时可见的 stale；不为“实时”无限增加目标集群压力。
- 接受 API、Collector 和 Worker 部署数量增加，换取故障与资源隔离；共享数据库仍是风险，不能承诺吞吐线性增长。
- 目标限定为上述数据规模和使用场景。持续高于 Event 预算、更大单集群或更高用户并发需要重新测量；集群数量不是唯一容量指标。


## 10. 第三批实施边界（2026-10-21）

- `COLLECTION_SHARDS=16` 仅允许共享 MySQL，并要求 `HEALTH_INSTANCE_SOURCE=workloads`。首次认领持久化 shard 数，后续不同 shard 数或旧模式采集器启动失败，禁止两套采集方式重叠。分片数量迁移／回滚需要停所有采集器、备份并受控迁移映射；不能直接把环境变量改回 0。
- 健康共享 12 槽，容量／索引／Event 初始 List 共享 4 槽，每集群每通道 1 槽；SQL 租约跨副本生效。进程内先有界准入，避免大量任务同时竞争 SQL 配额。排队最多 5 分钟，取得槽位后才开始计算单次执行超时；owner 取消会同时终止排队与执行。API 实时通道与采集通道目前仍各有预算，尚非统一远端预算。
- Kubernetes List 每页 500 项、响应体最多 8 MiB、每资源种类最多 25,000 项，检查 continuation 与 resourceVersion。失败／410／忽略分页／超额均放弃本轮，不提交部分索引。Pod／Node 使用逐页摘要与聚合，避免保留完整对象全集；Event message 最多保留 4,096 字节。最终摘要仍随单集群对象数增长，受对象上限和共享并发约束。
- 索引目前仍采用完整成功批次的事务替换，并非 UID 增量更新；MySQL 使用 READ COMMITTED 减少空范围 gap lock，死锁／锁等待最多重试整个幂等事务 3 次。容量／健康／索引／Event／水位写入均检查所有权。
- 资源搜索增加每 API 进程 32 项、每项至多 256 KiB 的摘要缓存，正常 TTL 10 秒、pending 1 秒，同查询合并，最多 4 个并行 SQL 查询。授权未来按集群范围收紧时必须将范围加入缓存 key。
- `cmd/fleetscale` 提供独立 TLS endpoint、真实分页解码与共享 MySQL 的可复现模拟；两个 API／Collector 是同一进程内的逻辑实例。短时模拟不替代真实集群、独立 Pod 故障与 24 小时验收。

第三批短时压测追加：MySQL 事件问题概览已采用集合聚合（最多两次 SQL，逐集群选择 daily/raw），不再逐集群发起约 2N 次聚合。MySQL 名称前缀查询先走名称索引并限制候选数；候选不足时仍保留名称／命名空间／owner／image 的原子串匹配回退。冷子串查询与多样关键词压力尚待单独验收。API 数据库连接池需与 Collector 隔离；模拟工具各 API 使用独立池，避免错误地把所有角色压进一个 20 连接池。

短时实测与参数限制见 [2026-10-21 模拟报告](../performance/2026-10-21-fleet-100-synthetic.md)。全部 962 次 HTTP 请求成功不代表第 7 节完整验收通过。
