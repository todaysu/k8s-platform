# ADR-0003：Kubernetes 多副本与统一 MySQL

## 状态

Accepted

## 背景

平台将部署到 Kubernetes，目标纳管 60+ 集群、每套约 200 个节点。SQLite 只能支撑本地单副本；多个平台副本同时运行健康与 Event 采集会造成重复扫描。用户希望后续单独接入 MySQL，并由平台自动初始化所需表。

## 决策

1. 新增 `PLATFORM_DATABASE_DSN`。配置后，集群元数据、健康快照、容量基线、Event、用户和会话统一存入 MySQL 8.4；未配置时使用 SQLite 开发模式。
2. 平台启动时获取 MySQL advisory lock，执行幂等 DDL，然后才启动 HTTP 服务。多个 Pod 可同时启动但不会并发迁移。
3. Kubernetes 中使用 `coordination.k8s.io/Lease` 选主，只有 Leader 运行健康与 Event 采集；所有副本均提供只读 API 和交互查询。
4. 全局概览继续读取持久化快照。单集群详情按需访问目标集群。
5. 不在中央平台长期保存所有 Pod 对象。60 套集群可能产生数十万 Pod，中央 Informer 会显著增加内存、连接与重连风暴风险；首个生产版本采用每集群每分钟一次、全局并发受控的快照采集。

## 结果

### 正面

- MySQL 接入后自动初始化，无需人工执行 SQL。
- 平台可滚动升级、多副本运行且不会重复采集。
- 页面访问量不影响目标 Kubernetes API 压力。
- 单集群故障与数据库迁移互相隔离。

### 负面

- 健康数据存在约 1～2 分钟延迟。
- 中央平台仍会周期性 List Pod；需通过并发、超时和错峰控制压力。
- MySQL 成为平台共享依赖，需要备份与监控。

## 备选方案

- **每个集群安装 Agent/Informer**：规模更大时更优，但违背当前非侵入式约束。
- **中央持有全部 Informer**：实时性高，但 60+ 集群的长连接、对象内存和重连成本过高。
- **Kafka/Redis**：当前采集量不需要，引入后会提高部署和故障处理复杂度。
