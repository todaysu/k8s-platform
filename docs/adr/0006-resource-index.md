# ADR-0006：使用持久化资源索引支撑跨集群搜索

- 日期：2026-10-20
- 状态：已接受，补充 ADR-0005 的搜索决策

## 背景

ADR-0005 通过 singleflight 和 120 秒缓存降低了并发重复加载，但缓存过期后的首次搜索仍要访问全部纳管集群，每套集群需要 5 次工作负载 List 和 2 次 Pod List。60 套集群时，单次冷搜索约 420 次 List，接口超时和 API Server 压力都不可接受。

## 决策

1. 平台在自身数据库维护 `cluster_resources` 摘要表，只保存搜索需要的字段：集群、类型、Namespace、名称、状态、Owner、节点和镜像。不保存完整 Kubernetes 对象。
2. 资源索引由 Leader 上的后台采集器维护，默认每 10 分钟刷新一套集群；首次启动不按间隔错峰，尽快完成首轮构建。
3. 浏览器搜索只查询 `cluster_resources`，请求路径不访问目标集群。只有在索引完全为空（首次构建尚未完成）时才回退到 ADR-0005 的受控实时加载。
4. 平台删除集群时同步删除索引；MySQL 使用外键级联，SQLite 额外显式删除。
5. 索引刷新失败时保留上一版索引，不用空结果覆盖；搜索可能短暂显示旧数据。

## 后果

### 正面

- 搜索请求的集群 API 调用从 O(集群数) 降为 0。
- 搜索延迟与集群数量基本无关，只与索引行数和匹配度有关。
- 索引行数约为 60 × 6,000 Pod + 工作负载，处于单机 MySQL 可承受范围。

### 负面

- 搜索结果最多滞后一个索引周期（默认 10 分钟）。
- 索引采集本身每套集群每轮需要 7 次 List，但频率远低于按用户搜索触发的 fan-out。
- 首次构建期间索引逐步完整，搜索结果可能暂时缺少部分集群；构建完成后不再回退实时加载。

### 中性

- 索引是摘要，不包含标签选择器、容器状态等完整详情；需要精确证据时仍进入集群详情。
- 索引表可以后续扩展全文索引或按集群分区，不改变 API 契约。
