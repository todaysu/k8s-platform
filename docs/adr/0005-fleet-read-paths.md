# ADR-0005：跨集群读路径改为数据库聚合与快照

- 日期：2026-10-20
- 状态：已接受

## 背景

平台按 60 套集群、每套约 200 节点设计。原实现存在三条会随集群数线性放大的请求路径：

- 跨集群事件每次请求顺序扫描全部集群、全部时间窗口的原始 Event，并在 Go 中聚合；
- `resources` 视图对每套集群实时 `List Pods + ReplicaSets` 解析工作负载归属；
- 集群详情与容量页每 30 秒实时访问目标集群，绕过后台快照；
- 跨集群搜索没有 singleflight，多个用户同时搜索会重复拉取全部集群。

## 决策

1. 跨集群事件的 issues/objects 视图使用 SQL `GROUP BY` 聚合，只返回聚合行；`event` 视图保留原始行，但仅用于单集群、短时间窗的证据查询。
2. 工作负载归属只在查询已经限定到单套集群时解析，并按集群缓存 5 分钟；全集群视图不调用任何目标集群 API。
3. `GET /clusters/{id}` 与 `GET /clusters/{id}/capacity` 默认读取采集快照；`refresh=1` 才实时采集。容量实时刷新会回写快照，保证新建基线立即可见。
4. 跨集群搜索按集群 singleflight，结果缓存 120 秒，接口超时 30 秒；缓存仍保存资源摘要，不保存完整 Kubernetes 对象。该请求路径随后由 ADR-0006 的持久化资源索引取代，singleflight 仅保留为索引为空时的降级。
5. 列表读取使用 `ResourceVersion: "0"` 和 protobuf 响应，避免每次刷新都从 etcd 做 quorum read，并降低大列表的解码成本。

## 后果

### 正面

- 跨集群请求的数据库扫描次数与返回数据量不再随原始 Event 数量线性增长。
- 页面轮询只读平台数据库，不再放大目标集群 API Server 压力。
- 多人同时搜索同一集群只触发一次加载。

### 负面

- 全集群 `resources` 视图不再自动把 Pod 事件归并到工作负载；需要先选择一套集群才能看到归属。
- 详情页快照最多滞后一个采集周期（健康 1 分钟、容量 5 分钟），需要实时值时必须点击刷新。
- issues 的 `affected_objects` 按类别求和，同一对象跨类别时可能重复计数。

### 中性

- 原始 Event 表仍保留，用于证据与后续 AI 分析；小时聚合表暂未作为 issues 的查询来源。
