# ADR-0002：使用后台健康快照替代页面实时全量扫描

## 状态

Accepted

## 背景

目标规模为 60 套以上集群、每套约 200 个节点。当前 `GET /api/v1/clusters` 会在每次请求中并发访问所有纳管集群，逐集群列出 Node、Pod、Service 并查询 Prometheus。浏览器每 30 秒请求一次，访问用户数会直接放大 Kubernetes API 压力，并且单个慢集群会拉长整个页面响应。

## 决策

1. `GET /api/v1/clusters` 只读取平台数据库中的最近健康快照，不再连接 Kubernetes API。
2. 在现有模块化单体内增加独立 `HealthCollector` 后台角色，第一阶段每 60 秒完成一个错峰采集周期，最多并发 5 套集群，每套最多执行 20 秒。
3. 健康采集成功时持久化 Node、Pod、核心组件、Worker、API 延迟和 Prometheus 当前使用率；失败时标记连接失败，并保留最后一次成功快照及其时间。
4. 单集群节点、工作负载、日志、Exec 等详情继续按需实时查询目标集群。
5. 第一阶段继续使用 SQLite 保存快照，以最小改动解除 HTTP 请求与集群扫描的耦合；生产多副本前必须将元数据迁移到共享 MySQL，并为 Collector 增加 Leader Election。

## 结果

### 正面

- 页面用户数不再放大 Kubernetes API 请求量。
- 全局概览响应时间与集群数量基本解耦。
- 单集群故障不会阻塞其他快照写入。
- 为后续 List + Watch 增量索引和 API/Collector 分离建立稳定边界。

### 负面

- 页面展示的是最多约 60～120 秒前的快照，不是请求瞬间的实时状态。
- 第一阶段后台采集仍会周期性全量 List Pod；在完成 List + Watch 改造前，Pod 数量很大时仍有控制面压力。
- 单实例 SQLite 阶段仍不具备平台高可用能力。

## 备选方案

### 继续由页面触发实时采集

不采用。实现简单，但用户数和刷新频率会线性放大目标集群压力。

### 立即引入 Kafka、Redis 和独立微服务

暂不采用。当前主要问题是采集触发方式，而不是消息中间件吞吐；会显著增加首版运维复杂度。

### 立即为全部资源建立 Informer

作为下一阶段目标。它能消除周期性全量 Pod List，但涉及资源索引、重连、内存上限和 Leader Election，先以健康快照建立可测试边界。
