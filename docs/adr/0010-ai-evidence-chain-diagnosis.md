# ADR-0010：AI 分析从单集群症状复述改为证据链推理

- 日期：2026-10-21
- 状态：已暂停。2026-10-21 决定从当前产品与运行代码中移除 AI 分析模块，待需求重新确认后再评审，本文仅作为历史设计记录。
- 目标：让 AI 分析能给出可复核的根因结论，而不是复述用户已经看得见的状态数字
- 关联：ADR-0009（100 集群与 10 人并发承载架构）、ADR-0005（读路径聚合）、ADR-0006（资源索引）、ADR-0008（实例口径）
- 前置依赖：本 ADR 的阶段 0 依赖 ADR-0009 第 3、4 章的资源隔离与分片落地。在单 Leader 未拆分、客户端未统一限流前，不得启用本文的按需取证与多轮能力。
- 边界：本文是内部技术设计，允许记录被否决的方案与取舍理由。面向客户的方案材料另行编写，不直接引用本文的组件与实现细节。

## 1. 背景

平台已具备单集群只读 AI 分析（`internal/ai`）：对目标集群收集健康、容量、事件、工作负载、Pod、节点快照，交由 OpenAI 兼容接口生成带证据引用的结构化报告。实现质量本身没有问题——证据编号、引用校验、置信度分级、敏感信息脱敏、结果按证据哈希缓存、只读边界都已具备。

问题在于该功能在运维实际使用中价值有限。通读实现与使用路径后确认，缺口按影响排序为：

1. **证据缺层。** `ai.Source` 接口只有 `Get`、`GetCachedCapacity`、`GetEvents`、`GetWorkloads`、`GetPods`、`GetNodes` 六项，没有容器日志。模型看到的是 `pod-1 ns/web-xxx Running Ready 0/2 重启 47`，可以推断「容器反复重启」，但无法说明重启原因。平台已具备 `GetPodLogs` 能力，未接入 AI。排查「为什么重启」类问题，答案绝大部分在容器日志中，缺失该证据导致模型频繁输出「证据不足」或「建议查看日志」，即给出用户自行查看即可获得的结论。
2. **节点根因被截断。** `KubernetesConnector.Nodes()` 只读取 5 类 Node Condition 中的 `NodeReady`，且仅保留状态词。`MemoryPressure`、`DiskPressure`、`PIDPressure`、`NetworkUnavailable` 及其 `Reason`／`Message` 全部丢弃。节点 `NotReady` 时 kubelet 通常在 Condition Message 中写明根因（例如容器运行时网络未就绪），该信息当前不可达。`ClusterNode` 也缺少 `Conditions`、taint 等诊断字段。
3. **趋势不可得。** `queryPrometheus` 仅调用 `services/proxy/api/v1/query`（instant query），全库无 `query_range` 使用。AI 无法区分「配置长期如此」与「最近变更导致」，而这正是区分存量配置缺陷与本次变更引入故障的关键判据。
4. **时间窗口固定且静默。** `BuildEvidence` 将窗口硬编码为 `now-1h` 至 `now`，报告不声明实际窗口与截断情况。发版后次日复盘这类跨天问题无法覆盖，且用户会把抽样误认为全貌。
5. **仅单集群视角。** `Service.Create` 只接受 `scopeType == "cluster"`。平台在多集群维度已有的核心资产未被使用：`EventFingerprint` 跨集群聚合、共性指纹、容量基线对比、kube-bench 安全基线历史。
6. **一次性问答。** `BuildPrompt` 每次只发送 system 与单条 user，无对话历史与追问。排查本应是迭代过程，但当前无法追问上轮结论，也无法增量补证据。
7. **入口位置与真实排查流程不匹配。** `AIAnalysisPage` 的交互为「选集群 → 点按钮 → 等待 → 读报告」，`focus` 输入框位于选集群之后。运维的实际路径是在排查途中提问，而非暂停排查切换页面。

现有 Prometheus 接入、事件采集、资源索引、容量采集均为后台周期采集，与本文的「按需定点取证」是两种不同触发方式，需明确区分并各自受控。

## 2. 目标与非目标

### 目标

1. 证据覆盖到可判定根因的层级：容器日志、节点 Condition 全字段、指标趋势、事件关联。
2. 结论可复核：每条归因绑定真实证据，且置信度由确定性规则计算，不由模型自述。
3. 保留并放大多集群优势：共性问题优先由平台自身判定，AI 只处理平台无法解释的部分。
4. 排查可在进行中提问，支持追问与增量取证，不重复全量采集。
5. 分析结论可沉淀为可交付文档。

### 非目标

1. 不引入图数据库。Kubernetes 的 owner 关系是结构化数据，已由平台解析，不新增 Neo4j 及其运维成本。
2. 不在证据与准确率达标前开放自动修复执行。
3. 不追求报文级证据。全流量分析需要交换机镜像或分光，属另一类产品的能力边界，本平台不进入。
4. 不要求被纳管集群安装 Agent，不要求 Prometheus 对外暴露。

## 3. 决策

### 3.1 诊断入口由平台判定，而非外部告警推送

平台已有 `EventFingerprint`（对 `Type|Reason|RegardingKind|归一化 Message` 取 SHA256 前 16 位）与 `getFleetEventIssues` 的跨集群聚合能力。共性问题可由平台自身识别，无需等待 Alertmanager 推送。

- 建立「待解释问题」概念：由平台确定性逻辑产出，至少覆盖跨集群共性指纹、kube-bench 基线新增风险、容量基线漂移三类。
- AI 诊断入口从「按集群发起」改为「按问题发起」，问题携带 `clusterScope`（单集群或多集群）、`fingerprint`／`baselineId` 等定位信息。
- 告警联动（Alertmanager／企微／飞书）作为后续可选接入，不作为触发依赖。当前平台无任何 Alertmanager 接入，不将「等待外部推送」写为主链路。

**理由**：这是本平台相对单机工具的差异化能力，且依赖项已存在。等待外部推送会让 AI 在多数时间处于空转状态。

### 3.2 证据层补齐，按成本与收益排序

实施顺序即优先级，前四项不引入新架构：

| 项                | 改动                                                                                            | 成本                                                    | 解决的缺口   |
| ---------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------- | ------- |
| 节点 Condition 全字段 | `ClusterNode` 增加 `Conditions []NodeCondition`（含 `Type`、`Status`、`Reason`、`Message`）与 taint 信息 | 低。`Nodes()` 已取得原始对象，仅需透传，不新增 API 调用                   | 节点根因    |
| 事件按 Kind 配额      | 证据采集对 Pod／Node／其他分档配额，避免 Pod 类 Warning 挤占节点事件                                                 | 低。修改查询构造                                              | 节点维度在场  |
| 容器日志             | `Source` 增加 `GetPodLogs`，仅对异常 Pod 拉取尾部有限行，复用 `redactText` 脱敏                                  | 低至中。需定义单次行数与总字节上限                                     | 重启与崩溃根因 |
| 指标趋势             | 增加 `query_range` 调用与 trend 证据类型                                                               | 中。需遵守 ADR-0009 的 Prometheus 查询预算与硬超时                  | 变更相关性   |
| 依赖链证据            | `PodEvidence`／`WorkloadEvidence` 增加 `Chain []string`，由已解析的 owner 关系摊平                         | 低。`replicaSetOwnerMap`、`controllerOwnerReference` 已存在 | 因果链     |
| 节点日志             | 经 `nodes/proxy` 拉取 kubelet 日志                                                                 | 高。见 3.6                                               | 节点深层根因  |

日志取证范围限定为确定性规则已判定的异常 Pod，不对全部 Pod 拉取。行数与字节设硬上限，超限截断并在报告中声明，不静默截断。

### 3.3 置信度由规则计算，不由模型自述

当前 `Report.Confidence` 由模型输出，属自述，不可作为决策依据。改为：

- 命中确定性规则且证据链完整：`high`。
- 有证据但无规则匹配，模型归因与证据方向一致：`medium`。
- 证据不足或证据与结论冲突：`insufficient`。

模型输出的置信度字段保留为展示参考，不进入判定逻辑。模型归因与规则结论冲突时以规则为准，并在报告中显式指出冲突。

### 3.4 分层取证，单轮结构化输出优先

```
阶段 0  平台确定性判断（不调模型）
        跨集群共性指纹 / 安全基线偏离 / 容量漂移 → 产出待解释问题
                              │ 仅当平台无法解释
                              ▼
阶段 1  证据包 + 确定性规则（覆盖主要已知模式）
        按需定点取证：异常 Pod 日志、节点 Condition、指标趋势、事件、依赖链
        规则命中即直接给出结论，不调用模型
                              │ 规则未命中
                              ▼
阶段 2  LLM 归因（罕见路径，可接受更高延迟）
        单轮结构化输出，输入为规则结果 + 证据包 + 依赖链
```

模型调用为单轮，不使用多轮 ReAct 或运行时工具自主决策。原因：

- 现有分析服务为单 worker（`Service.run` 单 goroutine），`AnalysisTimeout` 默认 60 秒，队列容量 32。多轮工具调用在此并发与超时下不可靠。
- 先由确定性规则与证据收集决定「看什么」，成本、延迟与结果稳定性均优于让模型自主决定。

模型阶段只做规则覆盖不到的归因与自然语言解释，不负责决定取证范围。

### 3.5 诊断入口下沉至排查上下文

`AiAnalysisPanel` 由独立页面组件降级为可嵌入组件，在集群概览、Pod 详情、事件详情、节点详情页提供入口，自动携带当前上下文：

| 所在页面   | 携带上下文                  | 可直接回答         |
| ------ | ---------------------- | ------------- |
| 集群概览   | 集群                     | 当前集群是否存在异常    |
| Pod 详情 | 集群、命名空间、Pod 名、该 Pod 日志 | 该 Pod 为何重启／崩溃 |
| 事件详情   | 集群、事件 UID、关联对象         | 该事件反复出现的根因    |
| 跨集群事件  | 共性指纹、受影响集群集合           | 影响范围与共同根因     |

分析任务支持 `parentId` 形成对话链。每轮携带上轮摘要与用户追问，并复用已采集证据，避免重复拉取。证据缓存键由整集群哈希改为按 scope 计算，使增量追问只补采新增部分。

### 3.6 节点日志默认不接入

节点日志（kubelet 日志）默认不采集。理由：

- 采集需 `nodes/proxy` 权限，属敏感权限；平台当前无此授权，`deploy/platform.yaml` RBAC 亦无对应条目。
- kubelet 日志属于节点级敏感信息，在金融、能源等受监管场景需走权限审批流程。
- 节点 Condition 全字段已能覆盖主要节点根因；kubelet 日志属补充而非必需。

若后续确有需求，应作为独立请求处理：显式申请权限、用户主动触发、限流、审计，并在报告中标注该证据未经脱敏审查的部分。

### 3.7 报告可导出

`Result` 已包含证据、结论与建议，增加导出能力（Markdown 起步，Word 作为后续格式），用于故障复盘、值班交接与跨部门协同。导出内容需保留证据引用标识，便于回溯核对。

### 3.8 容量约束

本文所有能力受 ADR-0009 的预算与分片约束：

- 按需取证、指标趋势、日志读取均计入远端实时操作预算，不另开通道。
- 诊断任务在 Collector／Worker 侧的有界执行槽内运行，不得占用 API 普通读处理槽。
- 证据采集按 shard 归属校验 ownership epoch，避免旧 owner 写入过期结论。
- 单集群失败只影响该集群结论，不阻塞其他集群，也不阻塞平台其他页面。
- AI 队列与采集解耦；队列满时返回排队状态，不以拒绝用户操作换取达标。

### 3.9 实施顺序

| 阶段 | 内容                                             | 前置     |
| -- | ---------------------------------------------- | ------ |
| 0  | ADR-0009 资源隔离与分片落地；客户端与远端限流统一                  | —      |
| 1  | 证据层：节点 Condition、事件 Kind 配额、容器日志、`query_range` | 阶段 0   |
| 2  | 确定性规则集（对标 K8sGPT analyzer 范围），纯代码、零模型          | 阶段 1   |
| 3  | 待解释问题与按问题发起；跨集群指纹接入诊断入口                        | 阶段 2   |
| 4  | 依赖链证据化；置信度改由规则计算                               | 阶段 2   |
| 5  | 入口下沉与多轮追问                                      | 阶段 3、4 |
| 6  | 报告导出                                           | 阶段 4   |
| 7  | 依据阶段 1～4 的真实失败案例，评估是否引入 MCP 多轮工具调用             | 阶段 5   |
| 8  | 在诊断准确率达标且审计完备后，再评估「人工确认后执行」                    | 全部前置   |

阶段 8 刻意最后。在证据质量与准确率未建立前提供可执行命令，会把误判直接传导到生产。

## 4. 后果

### 正面

- 节点 Condition 与容器日志使多数常见根因可在单轮内判定，「证据不足」类输出显著减少。
- 置信度由规则计算后可用于决策与排序，不再依赖模型自述。
- 跨集群共性问题由平台判定，AI 调用量下降，且每次调用都有明确问题指向。
- 规则层覆盖常见模式后，LLM 成为罕见路径，成本、延迟与并发压力下降。
- 多轮追问使 AI 从一次性问答变为可迭代的排查助手。
- 不引入图数据库与 MCP，避免相应部署、备份与调试成本。

### 负面

- 证据层扩展使单次分析的远端调用增加，必须受 ADR-0009 预算约束；取证范围与行数上限需要按实测调优。
- 确定性规则集需要持续维护，随 K8s 版本与业务形态变化；规则漏报会直接导致 AI 阶段被频繁触发。
- 依赖链依赖 owner 关系完整性，孤儿对象、静态 Pod 与自定义控制器场景需单独处理。
- 规则置信度优先于模型判断，在规则过时或误匹配时可能给出错误的高置信结论，因此规则集必须带版本并可快速下线单条规则。
- 阶段 0 未完成前，本文的按需取证能力不得启用。

### 中性

- `Report.Confidence` 字段保留但语义改变，展示层需区分规则置信度与模型自述。
- 证据包结构变化会使既有 `EvidenceHash` 缓存失效一次，属预期。
- 全流量与报文级分析仍不在范围内；若客户确有该需求，属另一条产品线决策。

## 5. 被否决的方案

### 图数据库与 GraphRAG（Neo4j / SynergyRCA 路线）

否决。Kubernetes 的 owner 关系是结构化数据，平台已通过 `replicaSetOwnerMap`、`controllerOwnerReference` 及 `OwnerKind`／`OwnerName` 字段解析。依赖链按需拉取后在内存构建邻接表即可，计算量小且无状态。

引入图数据库的额外成本包括：独立部署与备份、schema 迁移、跨 60～100 套集群的分片策略（各集群资源关系彼此独立，单图表达受限）、以及团队新增运维负担。目标收益（引导归因）可用确定性代码遍历达成。

### 立即引入 MCP 多轮 Agent 工具调用

否决，作为阶段 7 的候选。当前并发模型（单 worker、60 秒超时、队列 32）无法支撑多轮 ReAct；单轮取证已能覆盖多数场景；多轮自主决策在证据层未补齐时只会放大不确定性。

待阶段 1～4 完成后，以真实失败案例统计「缺少哪一类证据、哪一类工具能补」，再决定 MCP 接口设计，避免预先设计协议与工具集。

### 多智能体联邦（Supervisor + Logs/Metrics/Configs/Security Agent）

否决。当前问题不是缺少智能体分工，而是单次分析缺少证据。多个 Agent 并行会成倍增加模型调用与远端取证，而当前模型预算与队列不支持；且各 Agent 的取证范围在证据层补齐后可由同一证据包覆盖。

### 以 Alertmanager 推送作为唯一触发

否决。平台当前无 Alertmanager 接入，且等待外部推送会让 AI 在多数时间空转。平台自有共性指纹判定已具备数据基础，且是多集群平台的独有能力。

### 让模型输出可执行修复命令

当前阶段否决。现有实现把 `NextChecks` 统一标记为只读（`ParseReport` 中强制 `ReadOnly = true`），该设计保留。待阶段 8 且审计完备后再评估。

## 6. 待确认

1. **确定性规则集的来源与维护责任。** 对标 K8sGPT 的 23 个 analyzer 可作为初始范围，但其规则面向通用场景。本平台客户为 G01／OCP 技术栈（见 `Onboard` 的 `clusterType` 与 `technologyStack` 取值校验），规则是否需要按技术栈分化，需与实际故障分布核对后确定。
2. **容器日志的敏感信息边界。** `redactText` 当前覆盖 token／password／secret／authorization／api-key 与 bearer token。业务日志中的手机号、身份证号、订单号等业务敏感字段未覆盖。是否需要扩展规则，取决于客户的数据分级要求。
3. **`query_range` 的时间粒度与保留策略。** 趋势查询的默认步长、点数上限与是否落库，需结合 ADR-0009 的 Prometheus 查询预算确定。
