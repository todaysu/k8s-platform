# 容量 Namespace 分类与基线决策设计

## 1. 目标

平台在集群纳管后通过 Kubernetes API 发现 Namespace，由管理员从真实列表中完成业务与平台组件分类。分类结果用于容量汇总、交付基线和后续漂移监控，不修改被纳管集群。

## 2. 分类范围

- **业务 Namespace**：全平台共用一份规则，适用于所有环境和技术栈。
- **公共组件 Namespace**：适用于所有技术栈，例如 `kube-system`。
- **技术栈组件 Namespace**：分别为 `TCS`、`CMBK8S`、`OCP` 维护统一规则。
- **未分类 Namespace**：不匹配以上规则的 Namespace。不提供单集群分类例外。

同一 Namespace 不能同时出现在业务和组件规则中。保存时检测冲突并拒绝无效配置。

## 3. 发现与配置交互

全局容量页提供“容量分类配置”入口。页面按技术栈展示 Namespace 并包含：

- Namespace 名称；
- 出现的技术栈和集群数；
- Pod 数量；
- CPU/内存 Requests；
- 首次发现时间；
- 当前分类与规则版本。

管理员可单选或批量将 Namespace 标记为业务、公共组件或当前技术栈组件。保存后生成不可变的分类规则版本，容量快照返回所使用的规则版本。

## 4. 未分类资源

新发现且有 Pod 的 Namespace 标记为“新增·未分类”。它的 Requests 必须从可分配余量中扣除，并在容量条和表格中作为独立分类展示，避免高估容量。平台同时产生待处理提示，但不删除 Namespace、不停止 Pod，也不阻止查看容量。

## 5. 基线决策

将新 Namespace 分类为平台组件后，相应技术栈的平台固定开销口径发生变化。受影响集群进入“基线待决策”状态，可选：

1. **生成新基线**：保存新基线版本、分类规则版本、时间和变更说明。
2. **暂不更新**：必须录入原因，旧基线继续生效，状态显示为“差异已确认·未接受”。
3. **稍后处理**：保持待决策状态和持续提醒。

业务 Namespace 规则变化不自动要求重建平台固定开销基线。

## 6. 数据与安全

分类规则版本、Namespace 首次发现时间、基线决策和原因保存在平台 SQLite。Kubernetes API 仍是 Namespace、Pod 和 Requests 的事实来源。配置界面不提供创建、修改或删除 Kubernetes Namespace 的能力。

## 7. 验收要点

- 能从真实纳管集群发现 Namespace，无需手工输入名称。
- 业务分类全局生效，组件分类按技术栈生效。
- 新增未分类 Requests 从可分配余量中扣除。
- 技术栈组件分类变更后，受影响集群显示基线待决策。
- 选择不更新基线时原因必填，并可追溯历史记录。
