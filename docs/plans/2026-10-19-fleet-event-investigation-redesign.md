# 跨集群事件：从事件展示改为问题排查入口（设计草案）

## 目标

让运维人员回答四个问题：发生什么、影响哪里、证据是什么、下一步看什么。全局归并提供索引，排查落在具体集群、Namespace、原生工作负载或独立 Pod。复用现有 Event 采集和存储，不增加集群 Agent，不引入工单流程或自动修复。

## 现状与具体缺口

当前服务逐集群读取最多 200 条明细，再合并截断到最多 500 条；在这些采样明细上按 Type、Reason、Kind 和归一化消息生成指纹。前端每 30 秒刷新，默认最近 24 小时、全部类型。归并卡片只展示前 12 组，无分页、无查看影响对象的操作。原始列表只展示前 100 条；资源归属筛选仅在前端作用于明细，不改变问题组和指标。

2026-10-19 检查时接口返回 384 条 Event 记录、205 个归并组、29 个异常组、73 个资源对象。镜像拉取异常同时出现详细拉取错误、ErrImagePull、ImagePullBackOff，现有归并把它们展示为不同问题。

- 当前“需处理”只根据历史事件 Reason/Type 打分，未验证资源当前状态，因此历史 Warning 不能代表故障仍持续。
- “原始事件”保留了 Event UID 对应的记录及累计次数，并不是每次发生都留有一条独立历史。累计次数不能直接充当查询窗口内新增次数。
- 部分 Reason 只要包含 failed 就被统一标为严重，不能代表业务影响程度。
- 全局归并可以合并相似症状，但不能证明多个集群具有共同根因。
- 事件的业务/平台归属仍使用 kube-system/openshift 前缀硬编码，与全局业务 Namespace 清单不一致。

## 第一版界面

只保留两个入口：“异常排查”（默认）与“事件检索”（次级）。采集状态置顶短提示，存储保留天数、聚合行数放进“采集详情”，不占据排查主区。

### 1. 异常排查列表

默认展示最近 24 小时异常线索，Normal 生命周期事件不生成问题卡片。用可分页表格替代无操作卡片。默认筛选只有时间、集群、业务/平台、搜索；环境、技术栈、Namespace、资源类型放入展开筛选。

列：异常类别及证据摘要、影响集群、影响对象、最近发生、查看影响对象。

示例：

| 异常类别 | 证据摘要 | 影响集群 | 影响对象 | 操作 |
| --- | --- | --- | --- | --- |
| 镜像拉取异常 | 访问镜像仓库时代理连接被拒绝 | test01 | 若干 Pod | 查看影响对象 |
| 调度异常 | 事件记录出现节点 NotReady 污点 | 对应集群 | 若干 Pod | 查看影响对象 |

数量从查询结果计算，示例不固定写入产品。上方只显示异常类别、涉及对象、涉及集群、采集异常；历史异常不直接命名为“待处理”或“当前故障”。

归并方式：先按可解释的异常类别建立入口（镜像拉取、容器退出/重启、调度、存储挂载、探针、节点等）；同类别下按诊断特征分支保留仓库拒绝连接、认证失败、镜像不存在等差异，不能把所有 Failed 归为同一根因。未知 Reason 保留原始分组，不强行猜测。

所有筛选先在服务端生效，再计算同一范围的总量与列表。聚合从完整的持久化匹配集合计算，不从最近 500 条截断明细反推全量统计。列表和关联明细分别服务端分页，汇总缓存也必须包含完整筛选键。优先采用索引化查询与既有小时聚合，不能把全部历史明细拉进浏览器。

### 2. 查看影响对象

点击问题行，在侧边详情中保留当前问题和全局筛选。第一层展示按集群划分的影响对象，再选择具体对象：

- 集群 / Namespace；所属 Deployment、StatefulSet、DaemonSet 等原生控制器。
- Pod 名称、节点、当前状态、重启次数、最近相关事件。
- 无 ownerReference 的 Pod 显示“独立 Pod”，不虚构控制器。
- 优先关联对象 UID，追溯 Pod → ReplicaSet → Deployment；不凭名称前缀猜归属。
- UID 变更意味着资源已替换，不能将同名新资源冒充旧事件对象。

打开对象详情时才按需读取实时状态。展示“当前异常”“当前正常”“未核验”“资源已删除/替换”；采集或 API 不可用时显示未知，不能假定恢复。全局历史索引不自动扫描全部对象或把长时间没有事件视为已恢复。

### 3. 对象排查证据

同一个详情中顺序显示：

1. 当前状态：容器 waiting/terminated reason、退出码、重启数、节点及 owner 链；带核验时间。
2. 关键证据：完整、可复制的消息；保留镜像、仓库、端点、状态码等能判断故障的差异，长消息默认折叠。
3. 关联事件：仅当前问题及选中对象/已明确关联的 owner 和子资源，按时间排序；范围明确显示，例如最近发生前后 15 分钟。将 Warning 与 Scheduling/Pulled/Started 等 Normal 前后文一起按需呈现，重复记录显示首次/最近时间和累计次数。
4. 下一步：查看容器日志、上一次容器日志（已有数据支持时）、工作负载详情、节点；不支持的资源提供历史证据和受限说明。故障可能发生在容器启动前，届时说明暂无容器日志，不能只提供一个无效日志按钮。

诊断提示应是可追溯的规则提示。例如证据明确包含 proxy connect refused，可提示检查容器运行时代理和镜像仓库连通性；只出现 ImagePullBackOff 时只能说正在重试拉取，需查看前面的具体失败消息。事件未证实的原因必须标为可能原因，不能输出“已定位根因”。

跨集群同类症状只用于对比：先选集群/对象，再看证据差异。节点压力、调度失败、探针失败之间默认展示时间上相关的线索，不自动断言它们互为因果。

### 4. 事件检索

不再在默认页面下方铺满全量原始事件。独立次级入口保留时间、集群、Namespace、对象、Reason、类型、业务/平台筛选和服务端分页。Normal 默认收起，可显式查看。

从问题进入检索时自动携带问题指纹/诊断分支、集群、对象 UID 和时间范围；从对象进入时携带对象上下文。查询条件可见、可移除、可重置，返回时保留原问题列表筛选和页码。

每条记录可展开完整消息、Event UID、资源 UID、来源、首次/最近时间、累计次数；已删除资源仍能查看持久化历史。明示“累计发生次数”，如果使用小时增量展示窗口次数，标注其采集覆盖与粒度，不能伪装逐次事件时间线。

## 与全局规则和采集故障的关系

业务/平台直接复用全局业务 Namespace 清单。Node 与其他无 Namespace 的资源属于平台。清单未设置时所有带 Namespace 的资源也按平台统计，且提示业务清单未配置。

采集失败、历史保留截断和资源实时核验失败分别展示。某集群数据不可用时保留其他集群结果，显示缺失范围；“没有异常”与“没有采集到数据”必须区分。

## 验收场景

- 从 test01 的镜像拉取问题，看到具体 Namespace/Deployment/Pod 和仓库访问失败原文，不需要去全部事件里再次搜索。
- 同一资源出现 Failed 拉取、ErrImagePull、ImagePullBackOff，能在一个排查上下文中看到多个证据，不被当成三份独立任务。
- test01/myapp 中的 Deployment 与独立 Pod 显示正确归属和不同入口。
- 资源当前正常时保留历史证据，不能因历史 Warning 继续标为当前故障；API 超时不能标为恢复。
- 超过 12 个问题、100 条明细、500 条全局事件仍能分页查到；汇总和筛选一致。
- 归属筛选同时影响问题列表、影响数量、证据查询，和容量页面使用同一业务清单。
- 同名资源已被重建时按 UID 区分；已删除资源能够回看历史。
- 默认页没有全量原始事件长表，原始记录可以从问题精确下钻，也可以独立检索。
