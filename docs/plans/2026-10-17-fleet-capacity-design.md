# 全局资源池容量设计

## 1. 目标

将“容量”从单集群详情中的次级信息提升为平台一级运维视角。全局页回答整个资源池还有多少可调度余量、哪些集群最先耗尽、平台稳态是否漂移，以及容量结果是否因 Requests 缺失而不可信。

## 2. 信息架构

- 左侧主导航新增“容量”，路由为 `/capacity`。
- 全局容量页展示资源池汇总、风险发现和集群排行。
- 单集群“容量”页继续保留，承接全局列表的下钻，用于查看命名空间分布和管理交付基线。

## 3. 计算口径

全局比例不对集群百分比做算术平均。CPU 毫核和内存字节先跨集群汇总，再计算加权占比。

```text
可分配余量 = Allocatable
             - 平台 Requests
             - 业务 Requests
             - Pending Requests
             - 安全预留
```

CPU 和内存独立计算。Limits 只用于评估超卖，不从可调度余量中扣减。业务占比在摘要中取 CPU/内存 Requests 占比的较高值，避免低估单一维度压力。

## 4. 风险判定

- 高风险：CPU 或内存可分配余量不高于 5%。
- 需关注：最小余量不高于 20%，或存在业务 Requests 缺失，或基线漂移。
- 充足：不存在上述风险。
- 采集失败的集群不计入分母，页面单独告警，避免用零值污染容量汇总。

## 5. 采集与失败隔离

前端只请求一次 `GET /api/v1/capacity`。后端从已纳管集群读取容量快照，并发数限制为 6，单套失败只进入 `failures`，其他集群仍然可展示。页面每 60 秒自动刷新，也支持手动刷新。

## 6. 后续迭代

首版只展示实时快照。当 Prometheus 累积足够历史数据后，再增加 7/30 天 Requests 增长、峰值和耗尽趋势；不在没有真实时序数据时生成预测。
