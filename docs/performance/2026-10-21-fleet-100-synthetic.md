# 100 集群短时模拟验证（2026-10-21）

本报告验证中央采集／摘要存储／HTTP 读路径，不代表 100 个真实 Kubernetes 集群生产容量验收通过。目标仍是 ADR-0009 的 100 集群、10 人运维、24 小时混合故障场景。

## 环境与复现

- 工具：`cmd/fleetscale`；100 个独立本地 TLS Kubernetes 模拟 endpoint，client-go 校验证书、实际分页并解码对象。
- 每集群 200 Node、6,000 Pod、1,000 Deployment、2,000 ReplicaSet、100 Namespace；合计 20,000 Node、600,000 Pod、100,000 Deployment，持久索引 700,000 项。
- 两套逻辑 API、两套逻辑 Collector、16 shard、10 独立登录会话，运行于同一个 Go 进程；MySQL 版各 API 使用独立连接池（各最多 20 连接），采集端共用一个 20 连接池；**不是四个独立 Pod**。API 和 Collector 合并统计的 heap 还包含模拟接口开销。
- Go：`GOMAXPROCS=8`、`GOMEMLIMIT=1GiB`（软限制，不是容器硬内存上限）；数据库 MySQL 8.0 临时容器，2 CPU／2 GiB 上限。平台进程没有独立 cgroup CPU／RSS 限额。
- 流量为本机 TLS、无 WAN RTT。Prometheus 为小响应模拟；Event 初始列表为空、Watch 保持连接，没有事件风暴。真实证书／认证模式的成本不能据此推断。
- 生产式启动：保留健康／容量错峰，索引首次全量；未使用 `-fast-start`。全部索引与容量完成后，10 用户混合访问列表／容量／同一关键词搜索／事件摘要／监控 60 秒，每用户串行请求后停顿 500ms。最终复测的监控目标按用户分散到 10 套集群；此前所有用户共用一个监控目标，受每集群 2 槽限制的 429 不等同于数据库故障，两种场景不能直接等量比较。
- 结束时取消第一个 Collector，验证另一实例认领全部 16 shard。此为优雅退出；强制 kill／网络分区未在该工具中模拟。

```sh
# 先配置专用空 MySQL 数据库，库名必须以 ftc_scale_ 开头。
# FLEETSCALE_MYSQL_DSN 从私有环境传入，勿使用生产库。
GOMEMLIMIT=1GiB GOMAXPROCS=8 go run ./cmd/fleetscale \
  -clusters 100 -nodes 200 -pods 6000 -workloads 1000 -users 10 \
  -duration 60s -warm-timeout 8m -output /tmp/fleet-100.json
```

## 压测发现与修正

1. 大索引事务持有独占 owner 行锁会阻塞成员心跳。改为共享 fencing 行锁，成员租期单独续租；接管递增 epoch，提交前再次检查。MySQL 集成测试覆盖长事务期间心跳和旧 owner 写入拒绝。
2. 多集群首次 DELETE 空范围产生 InnoDB gap lock／死锁。索引事务改用 READ COMMITTED，1213／1205 最多重试整个幂等事务 3 次。
3. 大量等待任务同时竞争数据库配额。先通过进程内有界通道，再认领跨副本 SQL 配额，避免无界 SQL 竞争。
4. 排队时限原先传递给执行，导致排队接近时限的任务执行中途被取消。排队与执行使用独立 context；owner 取消仍贯穿二者，回归测试覆盖。
5. 配额续租数据库等待 1 秒过紧，取消的索引又需等默认 10 分钟重采。续租等待改为 5 秒（租期 15 秒、每 5 秒续租）；索引失败后 30 秒启动有界补采，不叠加并行轮次。超过分页预算的资源也会失败补采，持续超额需人工处理，不能无限提升预算。
6. Namespace 观察记录逐项写事务易增加竞争。改为快照批量事务、按稳定键排序写入，减少跨 shard 的锁顺序冲突。

另修正配额释放与过期清理的主键／到期索引锁顺序：释放也经过配额控制事务；并发 acquire／release 的实际 MySQL 测试覆盖。

早期未完成的运行均视为失败／中止，不计作通过结果；其问题用于修正上述路径。

## 测量结果

首次完成数据采集但混合访问失败的版本：冷启动 275.6 秒，优雅接管 3.786 秒，heap 峰值 135.75 MiB。119 次请求中仅 64 次成功；22 次客户端超时、5 次 429、20 次 500、8 次 503，普通接口 P95 约 5～10 秒。该结果未通过。

随后检查发现模拟工具把 API／采集器共用单个 20 连接池，与拆分部署不符，且 MySQL 的配额释放与过期清理锁顺序有冲突。工具已分离 API 池，配额释放已走相同控制事务。第二轮分离 API 池后：集群列表 P95 433.9ms、监控 P95 319.6ms，但搜索 P95 5,059.7ms、事件 P95 5,082.1ms、容量 P95 2,416.8ms。320 次请求中 250 次 200、30 次 429、40 次 500，仍未达标。接管 830ms；heap 峰值 144.80 MiB。

代码核对确认事件问题页按集群逐个聚合，24h 空数据也可产生约 200 条 SQL；资源搜索对 700,000 项进行宽匹配与排序。后续已加入 MySQL 集合聚合（最多两个查询，保留逐集群 daily/raw 回退）、名称前缀索引优先（候选不满预算时保留原宽匹配回退）。MySQL 测试验证 bulk 与逐集群结果一致、前缀和镜像子串搜索路径。非名称前缀的冷搜索仍走受限宽匹配，本轮不宣称所有搜索模式均已通过容量验收。

结束取消任务时会记录部分 context canceled／持久化失败日志；它们发生在 owner 退出和收尾阶段，不能与测量窗口的 HTTP 错误混算。旧 owner 迟到写入正确性由独立事务测试验证。采集器与 API 没有独立进程，因此该接管时延不能代替生产 kill／网络分区测试。

本次临时 MySQL 及其匿名卷在完成验证后清理；未重启现有开发后端或修改真实集群部署。相关 Go 包测试、race 和 go vet 通过；真实 MySQL 回归覆盖分片心跳／fencing、配额锁顺序、事件集合聚合 daily/raw 一致性和搜索两条路径。完整全库测试仍有此前记录的独立 AI 测试问题，未把相关包通过表述成全库通过。


## 已覆盖及剩余验收

Go 测试覆盖：分片均衡、成员过期接管、epoch 和错误 shard 写入拒绝、提交前过期检查、分页部分失败／忽略 limit／重复 continuation／单页字节限制、队列取消与执行分离、搜索共享加载不受单个调用者取消影响；实际 MySQL 验证心跳独立于数据事务以及迟到写入拒绝。

以下仍未验收：100 集群 24 小时稳定性；真实 200 节点集群与实际 Prometheus；独立进程 kill／网络分区；10% 集群离线；Event 突发与恢复；10 个真实终端；浏览器交互及渲染；不同关键词／冷搜索／大序列监控；20 RPS 基线与 50 RPS 突发；数据库慢查询／不可用。短时 heap 峰值不等同于长期无泄漏或独立 Pod RSS。

当前索引仍是完整成功批次事务替换，尚未实现 UID 增量更新；API 与采集远端预算仍分通道。当前结论不可用于省略剩余验收或直接承诺生产承载规模。
